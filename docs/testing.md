# Mewbell のテストの方針

この文書は、テストを書く・直す・削るときの方針を定める。コードの構造の約束は `docs/architecture.md` が、セキュリティの約束は `.claude/rules/security.md` が受け持つ。テストの実行の方法とツールの癖（`-only-testing` の渡し方など）は CLAUDE.md の「ビルドとテスト」にある。

テストは Swift Testing（`@Test`、`#expect`、`@Test(arguments:)`）で書く。レビューの指摘は、項目の ID（`T3` など）を添えて、`docs/architecture.md` の「指摘の仕分けとの関係」の表で扱う。

## 項目の足し方

- ID は `T1` からの通し番号で、再利用しない。廃止した項目は見出しを残す。
- 各項目には「方針」と「理由」を必ず書き、必要なら例を添える。例に書く型名やテスト名は、改名で古くなっても方針が読めるように、例の中だけに置く。
- 項目を足す・改めるときは、そのための change を起こす（振る舞いが変わらなければ `skip_specs: true`）。改めたときは `grep -rnw 'T<番号>' CLAUDE.md .claude openspec .swiftlint.yml docs scripts MewbellTests` で引いている箇所をすべて開き、新しい形と食い違わないかを確かめる。archive の design.md は当時の記録なので直さない。
- 今のテストが項目に合わなくなったら「既知の逸脱」に足し、直したら消す。

## 項目

### T1. 残すかは、削ったら見逃す現実的な不具合で決める

- **方針**: テストごとに「削ったら、どんな現実的な不具合を見逃すか」を言えるものだけを残す。言えないテストは足さず、見つけたら削る。カバレッジや件数は判断に使わない。次のテストは保証を足さない。
  - 型・コンパイラ・標準ライブラリが保証することの確認（合成された `Equatable` や `Codable`、enum の網羅）。種類の一覧の漏れは、`default` の無い `switch` でコンパイラに気づかせる
  - 本番のコードが通らない経路の確認（本番では渡さない引数、テストのためだけの入口）
  - 落ちようがないテスト（fake に割り込む仕組みが無いのに並行での取り違えを確かめる、など）
- **例外**: security.md で「ユニットテストで確かめる」とした性質は、確かめるテストの最後の 1 本を必ず残す。
- **理由**: 保証を足さないテストは、実行時間と、実装を変えるたびの修正の手間だけを増やす。件数を目標にすると、同じ分岐を確かめ直すテストが増える。

### T2. 分岐を確かめる場所は 1 か所にし、ほかの層・入口はその責務だけを見る

- **方針**: ある判断の分岐（境界、種類ごとの扱い）は、その判断を受け持つ型の単体テストでだけ網羅する。これをその分岐の正本と呼ぶ。値型や純粋な関数に切り出した判断（`docs/architecture.md` の A7）は、その型のテストが正本になる。上の層（actor・store・View）や別の入口（同じ関数を呼ぶ別のメソッド）のテストは、その層の責務（正しい引数で呼ぶこと、結果を正しく渡すこと）を代表 1 件で確かめるだけにし、分岐を確かめ直さない。
- **例**: ポーリング間隔の境界は `FeedDiagnosticsTests.derivesThePollInterval` が正本で、`PollingDiagnosticsTests.recordsTheIntervalAndTheNextFetch` は配線を 1 件だけ見る。リクエスト先の検査は `APIEndpointsTests.checksTheRequestURL` が正本になる。
- **理由**: 同じ分岐を層ごとに確かめると、仕様を変えるたびにすべてを直すことになり、どれが正本かも分からなくなる。上の層のテストは fake を組むぶん遅く、失敗したときに原因の場所も分かりにくい。

### T3. 期待値は仕様から書き、実装の式・表・文言・定数・手順を写さない

- **方針**: 期待値は、`openspec/specs/` の要件や API の仕様から、具体的な値で書く（表示する文字列そのもの、送るべき URL そのもの）。実装と同じ式・対応表・文言の組み立て・本体の定数の参照を、テストの中で組み直して期待値にしない。確かめるのは外から見える結果（返り値、送ったリクエスト、store の公開された状態、出した通知）で、内部の手順（どのメソッドを何回、どの順で呼んだか）ではない。
- **例外**: 回数や順序そのものが仕様のもの（API を叩く回数、間隔を空けて送ること、1 スレッド 1 通知）は、回数や順序を確かめる。
- **理由**: 実装を写した期待値は、実装が間違っていれば一緒に間違い、不具合を拾わない。内部の手順に頼るテストは、振る舞いを変えない書き換えでも壊れる。

### T4. 同じ分岐を通る入力は代表に絞る

- **方針**: `@Test(arguments:)` の引数や、よく似たテストは、通る分岐ごとの代表と、境界の両側に絞る。同じ分岐を通る入力を並べない。
- **例外**: security.md で「ユニットテストで確かめる」とした検証は、攻撃の形ごとの引数を削らない。たとえば `APIEndpointsTests.checksTheRequestURL` の、符号化した `..` の書き方ごとの引数は残す。
- **理由**: 同じ分岐の入力を並べても、実行時間と読む量が増えるだけになる。セキュリティの検証では、同じ分岐に見える形でも、デコードや正規化の段階ごとに別の箇所が拒んでいることがあり、1 つの形の取りこぼしがそのまま漏れになる。

### T5. fake は本物の契約どおりに振る舞わせる

- **方針**: fake は、差し替えている本物（OS の API や本体の型）が保証する振る舞いに合わせる。本物と違う振る舞いをする fake を前提にしたテストを書かない。fake そのものを確かめるテストは書かない。fake に足す機能は、本体のテストで要るものだけにする。
- **例**: `FakeHTTPTransport`、`FakeProcessRunner`、`FakeUserNotificationCenter`。
- **理由**: 本物と違う fake の上で通るテストは、本番で起きない違いを確かめ、本番で起きる不具合を見逃す。fake を確かめるテストは、本体の保証を何も足さない。

### T6. 実時間と同期的な待ちに頼らない

- **方針**: 時刻と待ちは注入したクロージャ（`now`、`sleep`）で制御し、テストで進める。非同期の処理の終わりは、テスト用のフックか、状態が変わるまで async で待って合わせる。状態を短い間隔で確かめ直し、期限を過ぎたら失敗させる待ち方はよい。固定の時間の `Task.sleep` や `Task.yield()` の回数で、起きるはずのことを待たない。fake の中では同期的に待たず（`Thread.sleep`、セマフォ）、止めるときは async で中断させる。
- **起きないことを確かめるとき**: 起きるならその前に来るはずの区切り（次の待ちに入ったこと、など）まで待ってから確かめる。区切りが無いとき（処理が止まって何も起きなくなる、など）だけ、短い固定の待ちの後に確かめてよい。この待ちは短すぎても見逃すだけで、誤って落ちることはない。
- **例**: 待ちを進めるのは `ManualSleeper`（時刻は別の `now` クロージャで動かす）、次の待ちに入ったことを待つのは `ManualSleeper.waitForSleeps`、状態が変わるまで待つのは `waitUntil`、終わりを待つフックは `AccountStore.waitForReload` と `SystemNotifier.waitForPendingWork`、fake を async で止めるのは `FakeHTTPTransport` の `pausedMethod`。
- **理由**: 実時間の待ちは遅く、負荷の高い機械では落ちる。`SWIFT_APPROACHABLE_CONCURRENCY` のため、fake で同期的に待つと呼び出し元の actor が塞がり、テストが止まる。
- **守り方**: `Thread.sleep` は lint の `no_thread_sleep` が止める。

### T7. 単体テストで確かめないものは、手元の確認として tasks に置く

- **方針**: 次のものは単体テストを書かず、手元で確かめる項目として change の tasks.md に置く。
  - 書体・色・ホバーの見た目
  - 読み上げ（ユニットテストの `NSHostingView` ではアクセシビリティの要素が作られない）
  - 本物の gh・ネットワーク・通知センターを通した動作
- **測るもの**: SwiftUI の実際の寸法や配置が要件にあるものは、`NSHostingView` に載せて測る。
- **理由**: 確かめられないものをテストにすると、通っても保証にならず、確かめたと誤解させる。

### T8. テストを足す・削るときの手順

- **足す**: T1 の問いに答えられることを確かめ、T2 の正本がすでに同じ分岐を確かめていないかを探す。正本があれば、新しいテストではなく正本に引数かケースを足す。
- **削る・統合する**:
  1. 削るテストの `#expect` ごとに、ほかのテストが同じ不具合を拾うか、統合先に移したかを確かめる。2 つのテストが互いに「もう一方で拾える」とされたら、残す側を先に決める。
  2. 残す側は、速い単体テスト、仕様を直接表すテスト、T2 の正本の順で選ぶ。
  3. 移した `#expect` は、実装を一時的に壊して落ちることを確かめる。
  4. `-only-testing` で対象のスイートを流す（渡し方と結果の確かめ方は CLAUDE.md の「ビルドとテスト」）。
  5. security.md の性質を確かめるテストを削るときは、性質ごとに残るテストを change の design.md に書く。
- **理由**: 統合のときに元のテストにしか無かった `#expect` を落としたり、互いを当てにした 2 本を両方消したりすると、気づかないまま保証が消える。
