# polling Specification

## Purpose
アカウントごとに Notifications API を繰り返し問い合わせるときの約束を定める。ポーリングの開始と停止、`If-Modified-Since` と `X-Poll-Interval` に従った間隔、失敗したときの待ち方、401 のときのトークンの取り直し、スコープ不足と認証エラーで止めることと再開のタイミングを対象とする。

## Requirements

### Requirement: ポーリングの開始と停止

Mewbell は、トークンをメモリに持っている（「使える」）アカウントごとに、独立してポーリングしなければならない（SHALL）。アカウントが初めて「使える」になったらすぐに最初の取得を始め（SHALL）、その後アカウントのトークンの状態が「取得中」や「トークンを取れない」に変わっても、ポーリングの状態（止まっていることを含む）を保たなければならない（MUST）。アカウントが一覧から消えたとき、全体の状態が「アカウントあり」以外になったとき、ユーザーが設定でそのアカウントを無効にしたとき、アプリが終了するときに、そのアカウントのポーリングを止めて取得した通知を捨てなければならない（MUST）。

1 つのアカウントで同時に走らせる取得は 1 つまでにしなければならない（MUST）。1 つのアカウントの失敗が、ほかのアカウントのポーリングに影響してはならない（MUST NOT）。

#### Scenario: 起動直後に取得を始める

- **GIVEN** Mewbell を起動し、`github.com/alice` のトークンを取得した
- **WHEN** `alice` が「使える」になる
- **THEN** すぐに `alice` の `GET /notifications` を送る

#### Scenario: ログアウトしたアカウント

- **GIVEN** `github.com/alice` と `github.com/bob` をポーリングしている
- **WHEN** ユーザーが `gh auth logout --user bob` を実行し、Mewbell がアカウントを読み直す
- **THEN** `bob` のポーリングは止まり、`bob` の通知は一覧から消える
- **AND** `alice` のポーリングは続く

#### Scenario: 1 つのアカウントだけ失敗する

- **GIVEN** `github.com/alice` と `ghe.example.com/dave` をポーリングしていて、`ghe.example.com` に接続できない
- **WHEN** 次の取得の時刻になる
- **THEN** `dave` の取得は失敗し、`alice` の取得はいつもどおり行われる

### Requirement: 無効にしたアカウントのポーリング

無効のアカウントをポーリングしてはならない（MUST NOT）。有効にし直したアカウントは、トークンを得たら初めて「使える」になったときと同じく最初の取得から始めなければならない（SHALL）。ただし、無効にする前にレート制限で待っていたときは、その再試行の時刻より早めてはならない（MUST NOT）。

#### Scenario: 無効にしたアカウント

- **GIVEN** `github.com/alice` と `github.com/bob` をポーリングしている
- **WHEN** ユーザーが設定で `bob` を無効にする
- **THEN** `bob` のポーリングはすぐに止まり、`bob` の通知は一覧から消える
- **AND** その後 `bob` の `GET /notifications` は送られない
- **AND** `alice` のポーリングは続く

### Requirement: 参加しているスレッドの切り替え

ユーザーが設定でアカウントの「参加しているスレッドだけにする」を切り替えたときは、そのアカウントのポーリングを止めて取得した通知を捨て、新しい `participating` の値で最初の取得から始め直さなければならない（MUST）。始め直した最初の取得には `If-Modified-Since` を付けてはならない（MUST NOT。切り替える前の `Last-Modified` は別の一覧のものなので）。持っているトークンは捨てずに使い続けなければならない（MUST）。ただし、そのアカウントの取得が「スコープ不足」か「認証エラー」で止まっているときは、新しい `participating` の値を覚えるだけで取得を始めてはならず（MUST NOT）、「止めたアカウントの再開」のときに新しい値で始めなければならない（MUST）。

#### Scenario: 参加しているスレッドだけにする

- **GIVEN** `github.com/alice` を `participating=false` でポーリングしていて、一覧に 8 件ある
- **WHEN** ユーザーが設定で `alice` の「参加しているスレッドだけにする」をオンにする
- **THEN** `alice` の一覧はいったん最初の取得中の表示になり、前の取得から 10 秒たっていればすぐに（たっていなければ 10 秒たったときに）、`If-Modified-Since` を付けない `GET /notifications?all=false&participating=true&per_page=50` が送られる
- **AND** `alice` のための `gh auth token` は実行されない

#### Scenario: 止まっているアカウントで切り替える

- **GIVEN** `github.com/alice` が「スコープ不足」で止まっている
- **WHEN** ユーザーが設定で `alice` の「参加しているスレッドだけにする」をオンにする
- **THEN** `alice` の `GET /notifications` は送られず、「スコープ不足」の表示のまま
- **AND** その後ユーザーが「再読み込み」を押すと、`participating=true` で取得が再開する

### Requirement: 参加しているスレッドの切り替えの後の最初の取得

「参加しているスレッドだけにする」を切り替えて始め直した最初の取得は、ユーザーの操作による取得として「再読み込み」と同じ下限に従い、切り替える前の最後の取得から 10 秒より早く送ってはならない（MUST NOT）。レート制限で待っているときは、切り替える前に予定していた再試行の時刻より早めてはならない（MUST NOT）。

#### Scenario: レート制限で待っているときに切り替える

- **GIVEN** `github.com/alice` の取得がレート制限で失敗し、2 分後に再試行する予定になっている
- **WHEN** ユーザーが設定で `alice` の「参加しているスレッドだけにする」をオンにする
- **THEN** `participating=true` の最初の取得は、その再試行の時刻まで送られない

### Requirement: 条件付きリクエスト

Mewbell は、アカウントごとに最後に受け取った `200` のレスポンスの `Last-Modified` の値をメモリに持ち、次の取得の 1 ページ目に `If-Modified-Since` として付けなければならない（MUST）。ただし、次のときは `If-Modified-Since` を付けてはならない（MUST NOT）: 値を持っていないとき（最初の取得、トークンを取り直した後）、そのアカウントで最後に `If-Modified-Since` を付けない取得の `200` ですべてのページを取り終えてから 5 分以上たったとき（システムの時計がその時刻より前に戻ったときも含む）、最後の取得の後にユーザーが再読み込みを押したとき。`304` を受け取ったときは、そのアカウントの通知の一覧を変えてはならない（MUST NOT）。

#### Scenario: 2 回目の取得

- **GIVEN** `github.com/alice` の最初の取得の 200 のレスポンスに `Last-Modified: Thu, 08 Oct 2026 12:00:00 GMT` があった
- **WHEN** Mewbell が 60 秒後に次の取得をする
- **THEN** 1 ページ目のリクエストに `If-Modified-Since: Thu, 08 Oct 2026 12:00:00 GMT` が付く

#### Scenario: 304 では一覧を変えない

- **GIVEN** `alice` の通知が 3 件表示されている
- **WHEN** 次の取得で API が `304` を返す
- **THEN** 表示は 3 件のまま変わらない

#### Scenario: 5 分ごとに条件なしで取り直す

- **GIVEN** `alice` の最後の条件なしの取得の `200` から 5 分たち、その間の取得は `304` か、条件付きの `200` だった
- **AND** その間に、`Last-Modified` より古い `updated_at` のスレッド `B` が未読になった
- **WHEN** Mewbell が次の取得をする
- **THEN** 1 ページ目のリクエストに `If-Modified-Since` が付かない
- **AND** 200 のレスポンスで一覧が置き換わり、`B` が表示される

#### Scenario: 条件付きの 200 では条件なしの取り直しを遅らせない

- **GIVEN** `alice` の条件なしの取得の `200` が 12:00 にあり、12:03 の条件付きの取得が `200` を返した
- **WHEN** 12:05 を過ぎてから最初の取得をする
- **THEN** 1 ページ目のリクエストに `If-Modified-Since` が付かない

#### Scenario: 再読み込みの後は条件なしで取得する

- **GIVEN** `alice` の最後の取得から 20 秒たっていて、`Last-Modified` より古い `updated_at` のスレッド `B` が未読になっている
- **WHEN** ユーザーが再読み込みを押す
- **THEN** 次の予定の時刻を待たずに `alice` の `GET /notifications` が `If-Modified-Since` なしで送られる（polling「ポーリングの間隔」）
- **AND** 200 のレスポンスで一覧が置き換わり、`B` が表示される

### Requirement: 条件付きリクエストの Last-Modified の更新

`Last-Modified` は、すべてのページを取り終えたときだけ更新しなければならない（MUST。`If-Modified-Since` を付けた取得でも付けない取得でも同じ）。

GitHub は `If-Modified-Since` を付けたリクエストに、`200` のときもその時刻より後に `updated_at` が進んだスレッドだけを返す。また `Last-Modified` には未読スレッドの `updated_at` の最新値を返すので、それより古いスレッドが後から未読になったときや、スレッドがほかの場所で既読になったときは `304` が返る。どちらの取得でも分からない一覧のずれ（増えた古いスレッドと、消えたスレッド）は、`If-Modified-Since` を付けない取得で直す。5 分はその取得から数える。

#### Scenario: 途中のページで失敗する

- **GIVEN** 1 ページ目の 200 に `Last-Modified: A` と `rel="next"` があり、2 ページ目の取得が失敗する
- **WHEN** Mewbell が次の取得をする
- **THEN** `If-Modified-Since` には前回すべてのページを取り終えたときの値（無ければ付けない）が付き、`A` は付かない

#### Scenario: ほかの場所で既読にしたスレッドが消える

- **GIVEN** `alice` の一覧にスレッド `C` が表示されていて、ユーザーが Web で `C` を既読にした
- **WHEN** 最後の条件なしの取得の `200` から 5 分たった後の取得をする
- **THEN** `C` は一覧から消える

### Requirement: 条件付きリクエストの一覧への反映

`If-Modified-Since` を付けない取得の `200` ですべてのページを取り終えたときは、そのアカウントの通知の一覧を、受け取ったスレッドで置き換えなければならない（MUST）。`If-Modified-Since` を付けた取得の `200` ですべてのページを取り終えたときは、受け取ったスレッドを今の一覧に重ねなければならない（MUST）: 同じ ID のスレッドは受け取ったもので差し替え、一覧に無いスレッドは足す。受け取ったスレッドに無いことを理由に、今の一覧からスレッドを外してはならない（MUST NOT）。重ねた後も、既読・Done・すべて既読で隠しているスレッドは一覧に出してはならない（MUST NOT。polling「スレッドの既読化の一覧に戻すまでと送らないとき」「スレッドの Done」「アカウントのすべて既読で外したスレッドの扱い」）。

#### Scenario: 条件付きの 200 は今の一覧に重ねる

- **GIVEN** `alice` の一覧に、条件なしの取得で受け取ったスレッド `A`（`updated_at` 11:00）、`B`（11:30）、`C`（12:00）が表示されていて、`Last-Modified` は `Thu, 08 Oct 2026 12:00:00 GMT`
- **AND** その後に `C` にコメントが付き（`updated_at` 12:05）、新しいスレッド `D`（12:06）が届いた
- **WHEN** Mewbell が `If-Modified-Since: Thu, 08 Oct 2026 12:00:00 GMT` を付けて取得し、API が `200` で `C`（12:05）と `D` だけを返す
- **THEN** 一覧には `A`、`B`、`C`（12:05 の内容）、`D` が表示される
- **AND** `A` と `B` の macOS の通知は取り下げられない
- **AND** 次の `If-Modified-Since` には、この `200` の `Last-Modified` が付く

#### Scenario: 条件付きの 200 は既読にしたスレッドを戻さない

- **GIVEN** `alice` の一覧に `A` と `B` が表示されていて、ユーザーが Mewbell で `B` を既読にし、その既読化のリクエストがまだ終わっていない
- **WHEN** `If-Modified-Since` を付けた取得が `200` で新しいスレッド `D` だけを返す
- **THEN** 一覧には `A` と `D` が表示され、`B` は表示されない

### Requirement: ポーリングの間隔

Mewbell は、成功した取得（`200` か `304`）の後、レスポンスの `X-Poll-Interval` の秒数と 60 秒の大きいほうだけ待ってから次の取得をしなければならない（MUST）。`X-Poll-Interval` が無いか数値でないときは 60 秒としなければならない（MUST）。待っている間にスリープしていた場合、復帰したときに間隔が過ぎていれば次の取得をしなければならない（SHALL）。

ユーザーの操作で、この間隔より早く取得してはならない（MUST NOT）。ただし、ユーザーが再読み込みを押したときは、取得を続けているアカウントについて、次の予定の時刻を待たずに取得しなければならない（MUST）。このとき、そのアカウントの前の取得を始めてから 10 秒たっていなければ、10 秒たつまで待ってから取得しなければならない（MUST）。ポップオーバーを開いただけでは早めてはならない（MUST NOT）。

#### Scenario: X-Poll-Interval に従う

- **GIVEN** 最後の取得のレスポンスに `X-Poll-Interval: 120` があった
- **WHEN** 最後の取得から 60 秒たつ
- **THEN** まだ次の取得はしない
- **AND** 120 秒たったところで次の取得をする

#### Scenario: 下限は 60 秒

- **GIVEN** 最後の取得のレスポンスに `X-Poll-Interval: 10` があった
- **WHEN** 最後の取得から 10 秒たつ
- **THEN** まだ次の取得はしない
- **AND** 60 秒たったところで次の取得をする

#### Scenario: 再読み込みですぐ取得する

- **GIVEN** `alice` の最後の取得を始めてから 20 秒たち、次の予定は 40 秒後
- **WHEN** ユーザーが再読み込みを押す
- **THEN** すぐに `alice` の `GET /notifications` が送られる
- **AND** その取得が成功した後は、そこから `X-Poll-Interval` と 60 秒の大きいほうだけ待って次の取得をする

#### Scenario: 再読み込みの連打は 10 秒に 1 回まで

- **GIVEN** `alice` の最後の取得を始めてから 3 秒しかたっていない
- **WHEN** ユーザーが再読み込みを押す
- **THEN** 取得を始めてから 10 秒たったところで `alice` の `GET /notifications` が送られ、それより前には送られない

#### Scenario: ポップオーバーを開いても早めない

- **GIVEN** `alice` の最後の取得から 20 秒しかたっていない
- **WHEN** ユーザーがポップオーバーを開く
- **THEN** `alice` の `GET /notifications` は送られない

### Requirement: 取得の途中とレート制限の間の再読み込み

再読み込み（「ポーリングの間隔」）が取得の途中で押されたときは、その取得が終わった後に、同じ 10 秒の下限を守って、もう 1 回取得しなければならない（MUST）。レート制限（polling「失敗したときの待ち方」）で待っているアカウントは、再読み込みを押しても早めてはならない（MUST NOT）。

#### Scenario: 取得の途中で押す

- **GIVEN** `alice` の取得のレスポンスがまだ返っていない
- **WHEN** ユーザーが再読み込みを押す
- **THEN** 返ってきた後、その取得を始めてから 10 秒たったところで、もう 1 回 `If-Modified-Since` なしで取得する

#### Scenario: 再読み込みで早めない

- **GIVEN** `alice` がレート制限で待っている（取得に API が `403` と `Retry-After: 300` を返し、まだ 300 秒たっていない）
- **WHEN** ユーザーが再読み込みを押す
- **THEN** 300 秒たつまで `alice` の `GET /notifications` は送られない

### Requirement: 失敗したときの待ち方

Mewbell は、取得が失敗したとき、そのアカウントで最後に取得できた通知の一覧を残したまま、次のように待ってから再び取得しなければならない（MUST）。

- 待ち時間が分かるレート制限（`403` / `429`）: `Retry-After` の秒数、または `X-RateLimit-Reset` の時刻まで待つ。どちらも 60 秒より短ければ 60 秒、1 時間より長ければ 1 時間待つ
- 拒否（レート制限でない `403`）、リクエストの誤り（`422`）、一時的な失敗、トークンを送る相手の確認やリダイレクトでの失敗: 60 秒から始めて失敗が続くたびに 2 倍にし、15 分を上限とする

- メモリにトークンが無かった（読み直しや取り直しで一時的に無いときなど）: リクエストを送らずに 60 秒待つ。失敗の回数には数えない

成功した取得の後は、待ち時間を 60 秒からに戻さなければならない（MUST）。

#### Scenario: 通信の失敗が続く

- **GIVEN** `ghe.example.com/dave` の取得が 3 回続けて通信の失敗になった
- **WHEN** Mewbell が次の取得の時刻を決める
- **THEN** 3 回目の失敗から 240 秒後に次の取得をする
- **AND** `dave` の一覧には最後に取得できた通知が残っている

#### Scenario: レート制限

- **GIVEN** API が `403` と `Retry-After: 300` を返した
- **WHEN** Mewbell が次の取得の時刻を決める
- **THEN** 300 秒後まで次の取得をしない

### Requirement: 待ち時間が分からないレート制限の待ち方

取得が失敗したときの待ち方（「失敗したときの待ち方」）には、次も含む。

- 待ち時間が分からないレート制限（github-api「ステータスコードの扱い」。待ち時間のヘッダーの無い二次レート制限の `403` と、待ち時間のヘッダーの無い `429`）: 「失敗したときの待ち方」の拒否などと同じく、60 秒から始めて失敗が続くたびに 2 倍にし、15 分を上限とする。失敗の回数は、「失敗したときの待ち方」の拒否などと合わせて数える

待ち時間が分からないレート制限で待っている間も、レート制限で待っているものとして扱わなければならない（MUST）。再読み込み（「ポーリングの間隔」）、「参加しているスレッドだけにする」の切り替え、無効にしてから有効に戻すこと（「無効にしたアカウントのポーリング」）で、その再試行の時刻より早めてはならない（MUST NOT）。取得の状態と最後の取得の失敗（「取得の状態」）は、レート制限にしなければならない（MUST）。

#### Scenario: 待ち時間が分からないレート制限が続く

- **GIVEN** `github.com/alice` の取得が 2 回続けて、待ち時間のヘッダーが無い二次レート制限の `403` になった
- **WHEN** Mewbell が次の取得の時刻を決める
- **THEN** 2 回目の失敗から 120 秒後に次の取得をする
- **AND** 取得の状態と最後の取得の失敗はレート制限になる
- **AND** `alice` の一覧には最後に取得できた通知が残っている

#### Scenario: 待ち時間が分からないレート制限の間に再読み込みを押す

- **GIVEN** `github.com/alice` の取得が、待ち時間のヘッダーが無い二次レート制限の `403` になり、60 秒後に再試行する予定になっている
- **WHEN** 20 秒後にユーザーが再読み込みを押す
- **THEN** `alice` の取得は予定の 60 秒後まで送られない

### Requirement: 401 のときのトークンの取り直し

Mewbell は、API が `401` を返したとき、そのアカウントのトークンをメモリから捨て、gh からトークンを 1 回だけ取り直して、すぐに取得をやり直さなければならない（MUST）。やり直すとき `If-Modified-Since` を付けてはならない（MUST NOT）。取り直したトークンでも `401` が返ったとき、またはトークンを取り直せなかったときは、そのアカウントを「認証エラー」にしてポーリングを止めなければならない（MUST）。止めたアカウントについて、ポーリングを自動で再開してはならず（MUST NOT）、ポーリングのためにトークンを取り直してもならない（MUST NOT）。ただし、トークンを捨てた後は、ポップオーバーを開いたときなどの通常の読み直しで、トークンを持っていないアカウントとして gh からトークンを取得してよい（MAY。accounts「読み直しのタイミング」）。

#### Scenario: トークンが失効していた

- **GIVEN** `github.com/alice` のトークンが失効し、gh には新しいトークンがある
- **WHEN** `alice` の取得で API が `401` を返す
- **THEN** Mewbell は `gh auth token --hostname github.com --user alice` を 1 回実行して新しいトークンを受け取る
- **AND** 新しいトークンで `If-Modified-Since` を付けずに取得をやり直し、通知が表示される

#### Scenario: 取り直しても 401

- **GIVEN** gh の `alice` のトークンも失効している
- **WHEN** `alice` の取得で API が `401` を返し、取り直したトークンでも `401` が返る
- **THEN** `alice` は「認証エラー」になり、ポーリングが止まる
- **AND** その後、ユーザーが再読み込みを押すまで `alice` の `GET /notifications` は送られない（ポップオーバーを開いたときの読み直しで `alice` のトークンが取得されても、ポーリングは再開しない）

### Requirement: スコープ不足で止める

Mewbell は、スコープの確認で「スコープ不足」になったアカウントのポーリングを止めなければならない（MUST）。止めたアカウントについて、自動で取得を繰り返してはならない（MUST NOT）。

#### Scenario: スコープの無いトークン

- **GIVEN** `github.com/alice` のトークンの `X-OAuth-Scopes` が `gist, read:org`
- **WHEN** `alice` の最初の取得が終わる
- **THEN** `alice` は「スコープ不足」になり、以後 `GET /notifications` は送られない

### Requirement: 止めたアカウントの再開

Mewbell は、「スコープ不足」か「認証エラー」で止めたアカウントについて、ユーザーが再読み込みを押したときに、トークンを捨てて gh から取り直し、`If-Modified-Since` を付けずに取得を再開しなければならない（MUST）。ポップオーバーを開いただけでは再開してはならない（MUST NOT）。

#### Scenario: スコープを足した後に再読み込みする

- **GIVEN** `github.com/alice` が「スコープ不足」で、ユーザーがターミナルで `gh auth refresh --hostname github.com --scopes repo` を済ませた
- **WHEN** ユーザーが再読み込みを押す
- **THEN** Mewbell は `alice` のトークンを gh から取り直し、`GET /notifications` を送る
- **AND** スコープが足りていれば `alice` の通知が表示される

#### Scenario: ポップオーバーを開いただけでは再開しない

- **GIVEN** `github.com/alice` が「スコープ不足」
- **WHEN** ユーザーがポップオーバーを開く
- **THEN** `alice` の `gh auth token` と `GET /notifications` は実行されない

### Requirement: 取得の状態

Mewbell はアカウントごとに、通知の取得について次のいずれかの状態を持たなければならない（MUST）: 最初の取得中、取得できた（最後に成功した時刻を持つ）、失敗して待っている（最後に取得できた通知と、次の取得の時刻を持つ）、スコープ不足、認証エラー。状態と通知は、アプリを終了したら残してはならない（MUST NOT）。

状態と一緒に、Mewbell はアカウントごとに次の値を持たなければならない（MUST）。

- 次の取得の予定時刻: 取得の後に待ち始めたときの、待ちが終わる時刻。止まっているときは持たない
- 最後の取得の失敗: 種類と時刻。種類は、通信の失敗、HTTP の状態コード（数字）、リダイレクト、レスポンスが大きすぎる、レスポンスの形が崩れている、トークンを持っていない、レート制限、のいずれかにする。後で取得が成功しても消さない（Diagnostics で最後の失敗を見られるように）

#### Scenario: 失敗して待っている

- **GIVEN** `github.com/alice` の通知を 12:00 に取得でき、12:01 の取得が通信の失敗になった
- **WHEN** Mewbell が `alice` の状態を決める
- **THEN** 状態は「失敗して待っている」で、12:00 に取得した通知と次の取得の時刻を持つ
- **AND** 最後の取得の失敗は「通信の失敗」で、時刻は 12:01

#### Scenario: 失敗の後に成功しても最後の失敗は残る

- **GIVEN** `github.com/alice` の 12:01 の取得が `502` になった
- **WHEN** 12:02 の取得が成功する
- **THEN** `alice` の状態は「取得できた」になり、最後の取得の失敗は「HTTP 502」、時刻 12:01 のまま残る

### Requirement: 取得の状態の打ち切り

状態と一緒に、Mewbell はアカウントごとに次の値を持たなければならない（MUST）。

- 打ち切り: 一覧が、10 ページで打ち切った取得の結果を含むか（github-api「通知の取得」）。`If-Modified-Since` を付けない取得の `200` で取り終えたら、その取得を打ち切ったかどうかにする。`If-Modified-Since` を付けた取得の `200` は、打ち切ったときだけ「打ち切った」にし、打ち切らなかったときは前の値を保つ（一覧の残りは前の取得のもののため）。`304` の後は前の値を保ち、止まった（スコープ不足・認証エラー）ときと、取得を最初からやり直したとき（「参加しているスレッドだけにする」の切り替え、無効にして有効に戻したとき）は「打ち切っていない」に戻す

#### Scenario: 打ち切った一覧の後の 304

- **GIVEN** `github.com/alice` の 12:00 の取得が 10 ページで打ち切られた
- **WHEN** 12:01 の取得が `304` を返す
- **THEN** `alice` は「打ち切った」のまま

#### Scenario: 打ち切った一覧の後の条件付きの 200

- **GIVEN** `github.com/alice` の 12:00 の条件なしの取得が 10 ページで打ち切られた
- **WHEN** 12:01 の条件付きの取得が `200` で 1 ページだけを返す
- **THEN** `alice` は「打ち切った」のまま

#### Scenario: 打ち切らなくなった

- **GIVEN** `github.com/alice` の 12:00 の取得が 10 ページで打ち切られた
- **WHEN** ユーザーが Web で多くの通知を既読にし、12:05 の条件なしの取得が 3 ページで終わる
- **THEN** `alice` は「打ち切っていない」になる

### Requirement: 取得の状態のポーリングの間隔とスコープ

状態と一緒に、Mewbell はアカウントごとに次の値を持たなければならない（MUST）。

- ポーリングの間隔: 最後の成功（`200` / `304`）の後に使った間隔（秒）と、それが `X-Poll-Interval` によるものか、既定の 60 秒か
- スコープ: 今のトークンで最後に受け取った `X-OAuth-Scopes` のスコープの名前の集合（ヘッダーが無いときは「無い」）。トークンを取り直したら捨てる

#### Scenario: 間隔とスコープ

- **GIVEN** `github.com/alice` の取得が `200` を返し、`X-Poll-Interval: 120` と `X-OAuth-Scopes: repo, read:org` が付いている
- **WHEN** Mewbell が次の取得まで待ち始める
- **THEN** `alice` のポーリングの間隔は 120 秒で `X-Poll-Interval` によるもの、スコープは `read:org` と `repo`、次の取得の予定時刻は 120 秒後になる

### Requirement: 取得の状態の値のやり直しと中身

取得を最初からやり直したときは、打ち切り以外の値も消して、持っていない状態から始めなければならない（MUST）。状態と一緒に持つ値に、トークン、API の URL、ヘッダーの生の値、レスポンスボディを入れてはならない（MUST NOT）。

#### Scenario: 取得をやり直すと値が消える

- **GIVEN** `github.com/alice` のポーリングの間隔、スコープ、最後の取得の失敗を持っている
- **WHEN** ユーザーが設定で `alice` の「参加しているスレッドだけにする」を切り替える
- **THEN** `alice` のポーリングの間隔、スコープ、最後の取得の失敗は消え、持っていない状態から始まる

### Requirement: スレッドの既読化

ユーザーがスレッドを開いたとき（ui「通知のスレッドを開く」、notifications「通知のクリック」）と、開かずに既読にしたとき（ui「スレッドの行の操作」）、Mewbell はそのスレッドをアカウントの未読の一覧からすぐに外し（SHALL）、そのアカウントのトークンで既読化のリクエスト（github-api「スレッドの既読化のリクエスト」）を送らなければならない（SHALL）。既読化のリクエストは、そのアカウントの取得の間隔や待ち時間（「ポーリングの間隔」「失敗したときの待ち方」）を変えてはならず（MUST NOT）、取得と並行して送ってよい（MAY）。既読化の結果にかかわらず、そのアカウントの次の取得は `If-Modified-Since` を付けない取得にしなければならない（MUST。既読化が `304` に隠れないように、また失敗したスレッドが次の取得で一覧に戻るように）。

#### Scenario: 一覧のスレッドを既読にする

- **GIVEN** `github.com/alice` の一覧に、スレッド `123` と `456` がある
- **WHEN** ユーザーがスレッド `123` を開く
- **THEN** `123` はすぐに一覧から消え、`456` は残る
- **AND** `PATCH /notifications/threads/123` が送られる
- **AND** `alice` の次の取得は、予定の時刻に `If-Modified-Since` を付けずに送られる

#### Scenario: 開かずに既読にする

- **GIVEN** `github.com/alice` の一覧に、スレッド `123` がある
- **WHEN** ユーザーが `123` の行の「既読にする」を押す
- **THEN** ブラウザは開かず、`123` はすぐに一覧から消える
- **AND** `PATCH /notifications/threads/123` が送られる

### Requirement: スレッドの既読化の一覧に戻すまでと送らないとき

外したスレッドは、既読化のリクエストが終わった後に送った取得の結果が出るまで、一覧に戻してはならない（MUST NOT。既読化より前に送った取得の結果に含まれていても戻さない）。アカウントが「スコープ不足」か「認証エラー」で止まっているとき、またはトークンをメモリに持っていないときは、既読化のリクエストを送らなくてよい（MAY）。

#### Scenario: 既読化が失敗する

- **GIVEN** ユーザーがスレッド `123` を開き、既読化のリクエストが通信の失敗になった
- **WHEN** 次の取得が成功し、`123` が未読のまま返る
- **THEN** `123` が一覧に戻る

#### Scenario: 取得中に既読にする

- **GIVEN** `alice` の取得のリクエストを送っている最中
- **WHEN** ユーザーがスレッド `123` を開く
- **THEN** 既読化のリクエストは取得の終わりを待たずに送られる
- **AND** その取得が `123` を含む結果を返しても、`123` は一覧に戻らない

### Requirement: スレッドの Done

ユーザーがスレッドを Done にしたとき（ui「スレッドの行の操作」）、Mewbell はそのスレッドをアカウントの未読の一覧からすぐに外し（SHALL）、そのアカウントのトークンで Done のリクエスト（github-api「スレッドを Done にするリクエスト」）を送らなければならない（SHALL）。一覧からの外し方、取得の間隔を変えないこと、次の取得を `If-Modified-Since` を付けない取得にすること、一覧に戻すまでの条件、止まっているときとトークンが無いときの扱いは、「スレッドの既読化」「スレッドの既読化の一覧に戻すまでと送らないとき」と同じにしなければならない（MUST）。同じスレッドへの既読化と Done が重なったときは、どちらのリクエストも終わった後に送った取得の結果が出るまで、一覧に戻してはならない（MUST NOT）。

#### Scenario: スレッドを Done にする

- **GIVEN** `github.com/alice` の一覧に、スレッド `123` と `456` がある
- **WHEN** ユーザーが `123` を Done にする
- **THEN** `123` はすぐに一覧から消え、`456` は残る
- **AND** `DELETE /notifications/threads/123` が送られる
- **AND** `alice` の次の取得は、予定の時刻に `If-Modified-Since` を付けずに送られる

#### Scenario: Done が失敗する

- **GIVEN** ユーザーがスレッド `123` を Done にし、Done のリクエストが `500` になった
- **WHEN** 次の取得が成功し、`123` が未読のまま返る
- **THEN** `123` が一覧に戻る

#### Scenario: 取得中に Done にする

- **GIVEN** `alice` の取得のリクエストを送っている最中
- **WHEN** ユーザーがスレッド `123` を Done にする
- **THEN** Done のリクエストは取得の終わりを待たずに送られる
- **AND** その取得が `123` を含む結果を返しても、`123` は一覧に戻らない

### Requirement: アカウントのすべて既読

ユーザーがアカウントの通知をすべて既読にしたとき（ui「すべて既読のボタン」）、Mewbell は、ユーザーが押したときにそのアカウントの一覧に表示していたスレッドの `updated_at` の最大値（秒未満は切り捨てる）を `last_read_at` として、すべて既読のリクエスト（github-api「すべて既読のリクエスト」）を送らなければならない（SHALL）。`last_read_at` を今の時刻や、押した後に届いたスレッドの `updated_at` にしてはならない（MUST NOT。見ていないスレッドを既読にしないため）。一覧が空のときは、リクエストを送ってはならない（MUST NOT）。

リクエストを送る前に、Mewbell はそのアカウントの一覧から `updated_at` が `last_read_at` 以前のスレッドをすぐに外さなければならない（SHALL）。

#### Scenario: すべて既読にする

- **GIVEN** `github.com/alice` の一覧に、`updated_at` が 12:00 と 12:30 のスレッドがある
- **WHEN** ユーザーが `alice` の通知をすべて既読にする
- **THEN** `alice` の一覧はすぐに空になる
- **AND** `PUT /notifications` が `last_read_at` を 12:30 として送られる
- **AND** `alice` の次の取得は、予定の時刻に `If-Modified-Since` を付けずに送られる

#### Scenario: 押した後に届いたスレッド

- **GIVEN** `alice` の一覧に 12:00 と 12:30 のスレッドが表示されている
- **WHEN** ユーザーがすべて既読を押し、リクエストを送る前に 12:45 のスレッドが届く
- **THEN** `PUT /notifications` は `last_read_at` を 12:30 として送られ、12:45 のスレッドは一覧に残る

### Requirement: アカウントのすべて既読で外したスレッドの扱い

外したスレッドは次のように扱わなければならない（MUST）。

- リクエストの結果が出るまでは、どの取得の結果からも `updated_at` が `last_read_at` 以前のスレッドを除く
- 既読にできた（`202` を含む）ときは、結果が出てから 5 分の間に送った取得の結果からも、`updated_at` が `last_read_at` 以前のスレッドを除く（`202` のとき、GitHub が既読にし終える前の取得で戻らないように）。`updated_at` が `last_read_at` より新しいスレッドは除かない。時計が結果の出た時刻より前に戻ったら、その後に送った取得の結果からは除かない
- 失敗したときは、結果が出た後に送った取得の結果から除かない（未読のままのスレッドが一覧に戻る）

#### Scenario: 非同期の既読化の途中の取得

- **GIVEN** ユーザーが `alice` の通知を 12:30 まで既読にし、API が `202` を返した
- **WHEN** その 1 分後の取得が、`updated_at` が 12:00 と 12:45 のスレッドを返す
- **THEN** 一覧には 12:45 のスレッドだけが出る

#### Scenario: すべて既読が失敗する

- **GIVEN** ユーザーが `alice` の通知をすべて既読にし、リクエストが通信の失敗になった
- **WHEN** 次の取得が成功し、前と同じスレッドが未読のまま返る
- **THEN** それらのスレッドが一覧に戻る

### Requirement: アカウントのすべて既読を続けて行ったとき

外したスレッドは次のように扱わなければならない（MUST）。

- すべて既読を続けて行ったときは、それぞれのリクエストについて「アカウントのすべて既読で外したスレッドの扱い」の規則を別々に当てはめる（後のリクエストの失敗で、前のリクエストの成功の分を戻してはならない（MUST NOT））

#### Scenario: 後のすべて既読が失敗する

- **GIVEN** ユーザーが `alice` の通知を 12:30 まで既読にして API が `202` を返し、その後 12:45 のスレッドが届いた
- **WHEN** ユーザーがもう一度すべて既読にし、そのリクエストが失敗した後の取得が 12:00、12:30、12:45 のスレッドを返す
- **THEN** 一覧には 12:45 のスレッドだけが出る

### Requirement: アカウントのすべて既読の後の取得と送らないとき

すべて既読の結果にかかわらず、そのアカウントの次の取得は `If-Modified-Since` を付けない取得にしなければならない（MUST）。すべて既読のリクエストは、そのアカウントの取得の間隔や待ち時間を変えてはならない（MUST NOT）。アカウントの取得の状態が「取得できた」でないとき（最初の取得中、失敗して待っている、「スコープ不足」か「認証エラー」で止まっている）、またはトークンをメモリに持っていないときは、リクエストを送ってはならず（MUST NOT）、一覧から外してもならない（MUST NOT）。

#### Scenario: 止まっているアカウント

- **GIVEN** `github.com/bob` が「スコープ不足」で止まっている
- **WHEN** Mewbell が `bob` の通知をすべて既読にしようとする
- **THEN** `PUT /notifications` は送られない

#### Scenario: 失敗して待っているアカウント

- **GIVEN** `github.com/alice` の取得が失敗して待っていて、最後に取得できた 2 件を持っている
- **WHEN** Mewbell が `alice` の通知をすべて既読にしようとする
- **THEN** `PUT /notifications` は送られず、2 件は一覧に残る

### Requirement: 操作の失敗の記録

既読化（「スレッドの既読化」）、Done（「スレッドの Done」）、すべて既読（「アカウントのすべて既読」）が失敗したとき、Mewbell はそのアカウントについて、失敗した操作の種類（既読・Done・すべて既読）、失敗の種類、時刻を記録しなければならない（SHALL）。失敗の種類は、認証エラー（`401`）、レート制限、通信の失敗、HTTP の状態コード（数字）、リダイレクト、トークンを持っていない（送らなかった）、のいずれかにしなければならない（MUST）。成功（github-api で操作ごとに成功とした状態コード）のときは記録してはならない（MUST NOT）。アカウントが「スコープ不足」か「認証エラー」で止まっていてリクエストを送らなかったとき、およびすべて既読を取得の状態が「取得できた」でないために送らなかったときは、記録してはならない（MUST NOT。止まっていることは取得の状態で伝わるため）。

#### Scenario: 既読化が失敗する

- **GIVEN** `github.com/alice` の一覧にスレッド `123` がある
- **WHEN** ユーザーが `123` を既読にし、`PATCH /notifications/threads/123` が `500` を返す
- **THEN** `alice` に、既読化が「HTTP 500」で失敗したことが知らせる失敗と最後の操作の失敗の両方として記録される
- **AND** `alice` の取得の状態と次の取得の予定時刻は変わらない

#### Scenario: すべて既読がレート制限になる

- **GIVEN** `github.com/alice` の一覧に 3 件ある
- **WHEN** ユーザーが `alice` の通知をすべて既読にし、`PUT /notifications` がレート制限の `403` を返す
- **THEN** `alice` に、すべて既読が「レート制限」で失敗したことが記録される

#### Scenario: 成功は記録しない

- **GIVEN** `github.com/alice` の一覧にスレッド `123` がある
- **WHEN** ユーザーが `123` を Done にし、`DELETE /notifications/threads/123` が `204` を返す
- **THEN** 操作の失敗は記録されない

### Requirement: 知らせる失敗と最後の操作の失敗

記録は 2 つの形で持たなければならない（MUST）。

- 知らせる失敗: ポップオーバーに出す（ui「操作の失敗の表示」）。失敗の結果が出た後に送った取得が成功（`200` / `304`）したら消さなければならない（MUST。失敗したスレッドはその取得で一覧に戻る）。失敗の結果が出る前に送った取得の成功では消してはならない（MUST NOT）。続けて失敗したときは、後の失敗で置き換えなければならない（MUST）。止まったときと、取得を最初からやり直したときは消さなければならない（MUST）
- 最後の操作の失敗: Diagnostics に出す。後で取得や操作が成功しても消さず、取得を最初からやり直したときにだけ消さなければならない（MUST）

記録に、トークン、スレッドの件名、API の URL、レスポンスボディを入れてはならない（MUST NOT）。操作の失敗は、そのアカウントの取得の状態・取得の間隔・待ち時間を変えてはならない（MUST NOT）。

#### Scenario: 次の取得で知らせる失敗が消える

- **GIVEN** `alice` の既読化が失敗し、知らせる失敗が記録されている
- **WHEN** その後に送った取得が `200` を返し、`123` が未読のまま一覧に戻る
- **THEN** 知らせる失敗は消える
- **AND** 最後の操作の失敗は残る

#### Scenario: 失敗の前に送った取得では消えない

- **GIVEN** `alice` の取得のリクエストを送っている最中に、ユーザーが `123` を Done にした
- **WHEN** Done のリクエストが `401` を返し、その後に先に送っていた取得が `200` を返す
- **THEN** 知らせる失敗（Done、認証エラー）は消えずに残る

#### Scenario: 取得をやり直すと消える

- **GIVEN** `acme.ghe.com/dave` に、Done の知らせる失敗と最後の操作の失敗が記録されている
- **WHEN** ユーザーが `dave` の「参加しているスレッドだけにする」を切り替える
- **THEN** `dave` の知らせる失敗と最後の操作の失敗はどちらも消える

### Requirement: スレッドのイベントの取得

Mewbell はアカウントごとに、一覧のスレッドのイベント（github-api「スレッドのイベントの決定」）と件名の状態（github-api「スレッドの状態の決定」）を取得し、スレッドの ID と `updated_at` の組ごとにメモリにだけ覚えなければならない（MUST）。種類が Release でリリースの ID を持つスレッド（`subject.url` が API ベース URL と同じオリジンで、パスが API ベース URL のパスに続く `repos/<owner>/<name>/releases/<1〜20 桁の数字>` で、`<owner>/<name>` がスレッドのリポジトリと一致するもの）については、イベントと状態の代わりにリリースのタグ（github-api「リリースのタグの取得のリクエスト」）を取らなければならない（MUST）。

1 つのアカウントで同時に取るスレッドは 4 件までにしなければならない（MUST）。

#### Scenario: 新着の Release のタグを取ってから知らせる

- **GIVEN** `github.com/alice` の前の取得の一覧にスレッド `555` が無かった
- **WHEN** 次の取得で、種類が Release で `subject.url` が `https://api.github.com/repos/octo/app/releases/413167889` のスレッド `555` が返る
- **THEN** `GET https://api.github.com/repos/octo/app/releases/413167889` が `alice` のトークンで送られる
- **AND** `555` を含む一覧は、`555` にリリースのタグを付けた状態で初めて知らされる

#### Scenario: リリースの ID を持たない Release

- **GIVEN** `github.com/alice` の種類が Release のスレッドの `subject.url` が無いか、`https://api.github.com/repos/other/repo/releases/1` のようにスレッドのリポジトリと一致しない
- **WHEN** Mewbell がイベントを取るスレッドを選ぶ
- **THEN** そのスレッドにはリクエストを送らない

### Requirement: スレッドのイベントの取得の run の ID

種類が `WorkflowRun` か `CheckSuite` のスレッドについては、イベントと状態の代わりに、そのスレッドのワークフローの実行（run）の ID（github-api「ワークフローの実行の検索のリクエスト」）を取らなければならない（MUST）。

#### Scenario: 新着の承認リクエストの run を取ってから知らせる

- **GIVEN** `github.com/alice` の前の取得の一覧にスレッド `777` が無かった
- **WHEN** 次の取得で、種類が `WorkflowRun` でリポジトリが `octo/app` のスレッド `777` が返る
- **THEN** `GET https://api.github.com/repos/octo/app/actions/runs?status=waiting&per_page=6` が `alice` のトークンで送られる
- **AND** `777` を含む一覧は、`777` に見つけた run の ID を付けた状態で初めて知らされる

#### Scenario: 種類が CheckSuite のスレッドは subject.url が無くても run を探す

- **GIVEN** `github.com/alice` の種類が `CheckSuite` のスレッドの `subject.url` が無く、件名が `CI workflow run failed for main branch`
- **WHEN** Mewbell がイベントを取るスレッドを選ぶ
- **THEN** そのスレッドは run を探す対象になる

### Requirement: スレッドのイベントの取得の記録

以下この要件とこれに続く要件の「イベント」は、イベントと状態の組と、リリースのタグと、run の ID を指す（イベントが「無い」でも状態は分かることがある）。覚えたイベントは、アプリの終了で捨て、ディスクや設定に書いてはならない（MUST NOT）。一覧のスレッドには、ID と `updated_at` がどちらも一致する覚えたイベントだけを付けなければならない（MUST）。`updated_at` が変わったスレッドのイベントは取り直さなければならない（MUST）。一覧から消えたスレッドの分は捨てなければならない（MUST）。アカウントが止まった（スコープ不足・認証エラー）ときは、すべて捨てなければならない（MUST）。

新着の判定に使う「前の一覧」と、捨てずに残す記録は、既読・Done・すべて既読で隠したスレッドを含む、API が返した一覧にしなければならない（MUST）（既読にできずに一覧に戻ったスレッドを、新着として取り直さないため）。

#### Scenario: 変わっていないスレッドは取り直さない

- **GIVEN** `github.com/alice` のスレッド `123` のイベントを `updated_at` 12:00 で覚えている
- **WHEN** 5 分ごとの条件なしの取得で、`123` が同じ `updated_at` で返る
- **THEN** `123` のイベントのリクエストは送られず、覚えたイベントが付く

#### Scenario: updated_at が進んだら取り直す

- **GIVEN** `github.com/alice` のスレッド `123` のイベント Commented by `bob` を `updated_at` 12:00 で覚えている
- **WHEN** 次の取得で `123` が `updated_at` 12:30 で返る
- **THEN** `123` のイベントを取り直し、Commented by `bob` は付けない

#### Scenario: 止まったら捨てる

- **GIVEN** `github.com/alice` のスレッドのイベントを覚えている
- **WHEN** `alice` が「認証エラー」で止まる
- **THEN** 覚えていたイベントはすべて捨てられる

### Requirement: スレッドのイベントの取得の対象

取得は、イベントの取得を待っている（取得したことが無いか、前回が一時的な失敗だった）番号を持つスレッド、リリースの ID を持つ Release のスレッド、種類が `WorkflowRun` か `CheckSuite` のスレッドのうち、既読・Done・すべて既読で一覧から隠しているもの以外だけを対象にし、「スレッドのイベントの取得の順」の順に行わなければならない（MUST）。

イベントが「無い」だったスレッドは、その `updated_at` の間は取り直してはならない（MUST NOT）。一時的な失敗と認証の失敗のスレッドは、次の機会に取り直さなければならない（MUST）。ただし、同じ `updated_at` のまま 3 回続けて失敗したスレッドは、その `updated_at` の間は取り直してはならない（MUST NOT）（リポジトリを移した後のリダイレクトのように失敗し続けるスレッドで、レート制限の残りを使い続けないため）。

#### Scenario: 失敗し続けるスレッド

- **GIVEN** `github.com/alice` のスレッド `123` のイベントの取得が、同じ `updated_at` のまま 3 回続けてリダイレクトで失敗した
- **WHEN** 次の取得が成功する
- **THEN** `123` のイベントのリクエストは送られず、`123` はイベントなしで一覧に出る
- **AND** `123` の `updated_at` が進んだら、また取り直す

### Requirement: スレッドのイベントの取得の順

1. 通知の取得が `200` で終わり、その前にもこのポーリングで一覧を取得できていたとき: 前の一覧に無かったスレッドと、前の一覧より `updated_at` が新しくなったスレッド（新着）のうち、更新日時が新しい順に最大 10 件のイベントを取ってから、その一覧を取得の状態として知らせる。この取得に 20 秒より長くかけてはならず（MUST NOT）、終わらなかったスレッドは一時的な失敗として扱う
2. 取得の状態を知らせた後（`200` でも `304` でも）、次の取得を待ち始める前に: まだ待っているスレッドのうち、更新日時が新しい順に最大 30 件のイベントを取り、取れたものを付けた一覧を知らせ直す。この取得にも 20 秒より長くかけてはならず（MUST NOT）、終わらなかったスレッドは一時的な失敗として扱う。同じ回の 1. で取ったスレッドは、失敗していても取り直してはならない（MUST NOT）

#### Scenario: 新着のイベントを取ってから知らせる

- **GIVEN** `github.com/alice` の前の取得の一覧にスレッド `123` が無かった
- **WHEN** 次の取得で `123` が返り、そのイベントが Commented by `bob` と決まる
- **THEN** `123` を含む一覧は、`123` に Commented by `bob` を付けた状態で初めて知らされる

#### Scenario: 最初の一覧はイベントを待たずに知らせる

- **GIVEN** `github.com/alice` のポーリングを始め、最初の取得で 12 件のスレッドが返る
- **WHEN** Mewbell が取得の状態を知らせる
- **THEN** 一覧はイベントを取る前に知らされ、その後で 12 件のイベントを取って一覧を知らせ直す

#### Scenario: 新着が多い

- **GIVEN** `github.com/alice` の次の取得で新着が 15 件ある
- **WHEN** Mewbell が取得の状態を知らせる
- **THEN** 更新日時が新しい 10 件はイベントを付けて知らされ、残りの 5 件はイベントなしで知らされる
- **AND** 残りの 5 件のイベントは、知らせた後に取って知らせ直す

### Requirement: スレッドのイベントの取得と再読み込み

この要件の 1. と 2. は、「スレッドのイベントの取得の順」の 1. と 2. を指す。1. と 2. の取得の最中にユーザーが再読み込みを押したら、その取得をやめて（取り終えた分は記録し、取れていない分は失敗として数えない）、再読み込みの取得を待たせてはならない（MUST NOT）。今の通知の取得の後にもう 1 回取得する再読み込みを待っている間（通知の取得の最中に押されたとき）は、1. と 2. の取得を始めてはならない（MUST NOT）。再読み込みで始めた取得そのものの 1. は、ほかの取得と同じく行わなければならない（MUST）。

#### Scenario: イベントを取っている間に再読み込みを押す

- **GIVEN** `github.com/alice` の取得の状態を知らせた後で、まだ待っているスレッドのイベントを取っている
- **WHEN** ユーザーが再読み込みを押す
- **THEN** イベントの取得はやめられ、再読み込みの取得はイベントの取得を待たない
- **AND** 取り終えたスレッドのイベントは記録され、取れていないスレッドは失敗として数えられない

### Requirement: スレッドのイベントの取得の結果の扱い

イベントの取得の結果（失敗とレート制限を含む）で、通知の取得の状態、打ち切り、ポーリングの間隔、連続した失敗の数、最後の取得の失敗（「取得の状態」）を変えてはならない（MUST NOT）。イベントの取得がレート制限になったら、制限が解ける時刻（ヘッダーで分からないか 60 秒より早いときは 60 秒後）まで、そのアカウントのイベントの取得を始めてはならない（MUST NOT）。その間も通知の取得は続けなければならない（MUST）。トークンを持っていないときはイベントを取ってはならない（MUST NOT）。イベントには、そのアカウントのトークンだけを付けなければならない（MUST）。

イベントを取っている間に既読・Done・すべて既読で一覧から外したスレッドを、イベントを付けて知らせ直すときに一覧に戻してはならない（MUST NOT）。ポーリングを止めた後に返ったイベントで、状態を書き換えてはならない（MUST NOT）。

#### Scenario: イベントの取得の失敗は取得の状態を変えない

- **GIVEN** `github.com/alice` の通知の取得が `200` で、イベントの取得が `502` になった
- **WHEN** Mewbell が取得の状態を決める
- **THEN** 状態は「取得できた」で、連続した失敗の数と最後の取得の失敗は変わらない
- **AND** そのスレッドはイベントなしで一覧に出て、次の機会にイベントを取り直す

#### Scenario: イベントの取得のレート制限

- **GIVEN** `github.com/alice` のイベントの取得が、10 分後に解けるレート制限になった
- **WHEN** 1 分後に通知の取得が成功する
- **THEN** 通知の取得の状態は「取得できた」で、10 分後までイベントのリクエストは送られない

#### Scenario: イベントを取っている間に既読にした

- **GIVEN** `github.com/alice` の新着のスレッド `123` のイベントを取っている
- **WHEN** その間にユーザーが `123` を既読にし、その後でイベントが返る
- **THEN** 知らせ直す一覧に `123` は戻らない

### Requirement: リポジトリのグループの既読化と Done

ユーザーがリポジトリのグループのスレッドをまとめて既読か Done にしたとき（ui「リポジトリの見出しの操作」）、Mewbell は、ユーザーが押したときにそのグループに表示していたスレッドだけを対象にしなければならない（SHALL）。押した後に届いたスレッドと、一覧に出ていない未読（「参加しているスレッドだけにする」で取得していないもの、500 件で打ち切って取得していないもの）を対象にしてはならない（MUST NOT）。リポジトリ単位の既読のエンドポイント（`PUT /repos/{owner}/{repo}/notifications`）を使ってはならない（MUST NOT）。対象が 0 件のときは何もしてはならない（MUST NOT）。

#### Scenario: グループを既読にする

- **GIVEN** `github.com/alice` の一覧に、`octo/app` のスレッド `1`（12:30）と `2`（12:00）、`octo/lib` のスレッド `3` がある
- **WHEN** ユーザーが `octo/app` のグループを既読にする
- **THEN** `1` と `2` はすぐに一覧から消え、`3` は残る
- **AND** `PATCH /notifications/threads/1` の結果が出てから `PATCH /notifications/threads/2` が送られる
- **AND** `PUT /repos/octo/app/notifications` は送られない
- **AND** `alice` の次の取得は、予定の時刻に `If-Modified-Since` を付けずに送られる

#### Scenario: 押した後に届いたスレッドは対象にしない

- **GIVEN** `octo/app` のグループにスレッド `1` と `2` を表示している
- **WHEN** ユーザーが `octo/app` のグループを既読にし、そのリクエストを送っている間の取得で `octo/app` のスレッド `4` が届く
- **THEN** `4` は一覧に出て、`PATCH /notifications/threads/4` は送られない

### Requirement: リポジトリのグループの既読化と Done のスレッドごとの扱い

対象のスレッドは、どれもすぐに一覧から外さなければならない（SHALL）。そのうえで、対象のスレッドごとに、既読は「スレッドの既読化」「スレッドの既読化の一覧に戻すまでと送らないとき」、Done は「スレッドの Done」に従わなければならない（MUST。リクエスト、一覧に戻すまでの条件、次の取得を `If-Modified-Since` を付けない取得にすること、止まっているときとトークンが無いときの扱い、notifications「通知の取り下げ」を含む）。

失敗は「操作の失敗の記録」に従って、既読か Done の失敗として記録しなければならない（SHALL）。1 回の操作で複数のスレッドが失敗しても、知らせる失敗は 1 つにしなければならない（MUST）。グループの操作は、そのアカウントの取得の間隔や待ち時間を変えてはならず（MUST NOT）、取得と並行して行ってよい（MAY）。

#### Scenario: グループを Done にする

- **GIVEN** `github.com/alice` の一覧に、`octo/app` のスレッド `1` と `2` がある
- **WHEN** ユーザーが `octo/app` のグループを Done にする
- **THEN** `1` と `2` はすぐに一覧から消え、macOS の通知も取り下げられる
- **AND** `DELETE /notifications/threads/1` と `DELETE /notifications/threads/2` が 1 件ずつ順に送られる

#### Scenario: トークンが無い

- **GIVEN** `octo/app` のグループにスレッド `1` と `2` があり、読み直しの途中で `alice` のトークンをメモリに持っていない
- **WHEN** ユーザーがグループを既読にする
- **THEN** リクエストは送られず、既読が「トークンを持っていない」で失敗したことが 1 つの知らせとして記録される
- **AND** `alice` の次の取得の結果で `1` と `2` が未読のまま返れば、一覧に戻る

### Requirement: リポジトリのグループの既読化と Done のリクエストの順

対象のスレッドへのリクエストは、一覧の並び順（更新日時が新しい順）に 1 件ずつ、前のリクエストの結果が出てから次を送らなければならない（SHALL。二次レート制限を避けるため）。リクエストの結果が認証エラー（`401`）かレート制限（`403` のレート制限、`429`）になったら、残りのスレッドへのリクエストは送ってはならない（MUST NOT）。送らなかったスレッドは、失敗したスレッドと同じく、その後に送った取得の結果で未読のままなら一覧に戻さなければならない（SHALL）。それ以外の失敗（`500` などの状態コード、通信の失敗、タイムアウト）では、残りのスレッドへのリクエストを続けなければならない（SHALL）。

#### Scenario: 途中でレート制限になる

- **GIVEN** `octo/app` のグループにスレッド `1`、`2`、`3` がある
- **WHEN** ユーザーがグループを Done にし、`DELETE /notifications/threads/1` がレート制限の `403` を返す
- **THEN** `2` と `3` へのリクエストは送られない
- **AND** `alice` に、Done が「レート制限」で失敗したことが 1 つの知らせとして記録される
- **AND** その後に送った取得の結果で `1`、`2`、`3` が未読のまま返れば、一覧に戻る

#### Scenario: 途中のスレッドが失敗しても続ける

- **GIVEN** `octo/app` のグループにスレッド `1`、`2`、`3` がある
- **WHEN** ユーザーがグループを既読にし、`PATCH /notifications/threads/1` と `PATCH /notifications/threads/2` が `500` を返す
- **THEN** `PATCH /notifications/threads/3` も送られる
- **AND** 知らせる失敗は、既読が「HTTP 500」で失敗したことの 1 つだけになる

### Requirement: リポジトリのグループの既読化と Done の途中で止まったとき

リクエストを 1 件送るたびに、その前にアカウントが止まっていないか、トークンをメモリに持っているかを確かめ直さなければならず（MUST）、送っている途中でアカウントが「スコープ不足」か「認証エラー」で止まったとき、アカウントの削除・無効化・アプリの終了でポーリングを止めたとき、トークンを捨てたときは、残りのスレッドへのリクエストを送ってはならない（MUST NOT。捨てたトークンを手元に持ち続けて送らないため）。送っている途中で止まったときは、それまでの失敗も記録してはならない（MUST NOT。止まっていることは取得の状態で伝わるため）。

#### Scenario: 送っている途中でアカウントを無効にする

- **GIVEN** `octo/app` のグループにスレッド `1`、`2`、`3` があり、ユーザーがグループを Done にして、`DELETE /notifications/threads/1` の結果を待っている
- **WHEN** ユーザーが `alice` を無効にし、Mewbell が `alice` のポーリングを止めてトークンを捨てる
- **THEN** `DELETE /notifications/threads/2` と `DELETE /notifications/threads/3` は送られない
- **AND** それより前に `DELETE /notifications/threads/1` が `500` を返していても、操作の失敗は記録されない
