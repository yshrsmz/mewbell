# Design

## Context

`@fission-ai/openspec` 1.14.1 の `openspec validate` は、要件の本文の長さを数えて 500 文字を超えると警告を出す（`MAX_REQUIREMENT_TEXT_LENGTH`。値は固定で、設定では変えられない）。本文は `### Requirement:` の見出しの次の行から、最初の見出し（ふつうは `#### Scenario:`）の前の行までで、空行とコードブロックの中を除き、各行の前後の空白を落として改行でつないだもの。長さは JavaScript の文字列の長さ（日本語は 1 文字 1）で数える。

main specs で 500 文字を超える要件は 52 件ある（最も長いのは github-api「ワークフローの実行の検索のリクエスト」の 3855 文字）。どれも、1 つの要件に複数の振る舞いの MUST / SHALL を段落で並べた形になっている。

delta spec の扱いは次のとおり（1.14.1 の `specs-apply` と `validator`）。

- `MODIFIED` は要件を丸ごと置き換える。本文だけでなく、残すシナリオもすべて書く必要がある
- `ADDED` の要件はアーカイブで spec の末尾に足される
- `validate <change> --strict` は `ADDED` の本文の長さを調べるが、`MODIFIED` の本文は調べない。アーカイブ後の main specs で調べる
- CI は `pnpm exec openspec validate --all --strict` を回す（`.github/workflows/ci.yml`）

## Goals / Non-Goals

**Goals:**

- main specs のすべての要件の本文を 500 文字以内にし、1.14.1 の `openspec validate --all --strict` を通す
- 規範の文とシナリオの中身を変えない。仕様が述べる振る舞いを変えない

**Non-Goals:**

- 文の言い換え、内容の整理や重複の削除、要件の統合
- 500 文字以内の要件の書き直し
- アプリのコード・テスト・ビルドの設定の変更
- `@fission-ai/openspec` の更新（PR #56 で行う）

## Decisions

### D1. 規範の文は言い換えずに、要件を振る舞いごとに分ける

長い要件は、段落や MUST / SHALL の文の区切りで分け、分けた先を新しい要件（`ADDED`）にする。分け方の規則は次のとおり。

- 規範の文（MUST / SHALL / MUST NOT / SHALL NOT / SHOULD などを含む文）は、一字一句変えずに、元の要件か分けた要件の本文に置く。シナリオへは移さない（シナリオは例なので、規範として弱くなる）
- 規範ではない文（例示、補足の説明、境界条件の言い換え）は、本文に残すか、その振る舞いのシナリオへ移してよい。シナリオへ移すときは、既存のシナリオの THEN / AND に足すか、新しいシナリオにする
- 分けた要件の本文が、それだけで読めるように、主語や前提（「ユーザーがスレッドを開いたとき」など）が前の段落にしか無いときは、前提を 1 句だけ補ってよい。補った句は規範の文の外に置くか、規範の文の頭に足す。足した句は PR でわかるように、tasks の保存の確認で一覧にする
- 「次のとき」「次の項目」のように箇条書きを受ける規範の文があり、その箇条書きを 2 つの要件に分けるときは、受ける文を一字一句同じまま両方の要件に置く。受ける文を言い換えたり、規範ではない前置きでつないだりすると、移した項目が規範の文を失うため。2 つの要件の項目を合わせると元の箇条書きと同じになる
- 受ける文が「次の X だけ」のように範囲を限る文で、重ねて置くと互いに矛盾するとき（github-api「スレッドのイベントの決定」の `event` の表）は、元の文の「次の X」を分けた要件の名前に置き換えて元の要件に残し、分けた要件には、元の文が受けていたもの（表の列）の使い方だけを述べる規範の文を 1 つ足す。新しい規範の文を足すのはこの場合だけで、足した文は保存の確認の一覧に入れる
- 1 つの要件の本文は 450 文字以内を目安にする（500 文字の上限に、後の小さな書き足しの余裕を残す）
- 分けた要件には、各要件の規範の文が述べる振る舞いを表すシナリオを、少なくとも 1 つ置く。既存のシナリオは消さず、その振る舞いを述べる要件の下へ移す。分けた要件に合うシナリオが既存に無いときだけ、その要件の規範の文から読み取れることだけを書いた新しいシナリオを足す
- 1 つの要件の中で互いに参照している文（「このとき」「上の場合」など）は、同じ要件に残すか、参照先が分かる名前（「「X」のとき」）に置き換える。置き換えたものも保存の確認の一覧に入れる

代替案: 規範の文をシナリオの THEN へ移して要件の数を増やさない案は採らない（ユーザーが選ばなかった。シナリオへ移すと規範として弱くなる）。

### D2. 名前と参照

元の要件には元の名前を残し、元の名前で参照されている振る舞い（ふつうは最初の段落）を残す。分けた要件には「<元の名前>の<振る舞い>」のように中身を表す名前を付け、同じ capability の中で重ならないようにする。

`openspec/specs/`・`docs/architecture.md`・コード・テストで `capability「要件名」` や `「要件名」` の形で参照している要件について、参照している中身が別の要件へ移ったときは、参照を移った先の名前に直す。中身が元の要件に残っているときは直さない。参照が、分けた要件のまとまり全体（元の要件と、そこから分けた要件）を指しているときも直さない。分けた要件は元の要件のすぐ後ろに並び、名前も元の名前から始まることが多いので、元の名前がまとまりの入口になる。`docs/architecture.md` を直すときはスキル `update-architecture-doc` に従い、`bash scripts/check-architecture.sh` を通す。

### D3. 目標の spec を先に作り、delta はそこから作る

capability ごとに、分けた後の main spec（分けた要件を元の要件のすぐ後ろに置いたもの）を作業用に作り、delta spec はそれと今の main spec の差から作る（中身が変わった要件は `MODIFIED`、足した要件は `ADDED`）。手で `MODIFIED` を書くと、残すシナリオを書き漏らしてアーカイブで消すおそれがあるため。

OpenSpec は、`MODIFIED` で今の main spec にあるシナリオを減らすことを許さない（`validate` がエラーにし、アーカイブも拒否する）。そのため、シナリオを分けた要件へ移すことは delta では表せない。delta の `MODIFIED` には、分けた後の本文と、元の要件のシナリオ（分けた要件へ移したものも含めてすべて）を入れ、移したシナリオはアーカイブの直後だけ元の要件と分けた要件の両方にある状態にする。

アーカイブでは `ADDED` が末尾に足されるので、アーカイブの後のコミットで、main spec を目標の spec に置き換える。このコミットで行うのは、分けた要件を元の要件のすぐ後ろへ並べ直すことと、元の要件に重ねて残したシナリオを消すことだけにする。アーカイブの結果と目標の spec の差が、この 2 つだけであることを確認スクリプトで確かめる。main specs をアーカイブの外で直すのはこのコミットだけにする。

代替案: 既存のシナリオを元の要件に残し、分けた要件には規範の文から新しいシナリオを書く案は採らない（ユーザーが選ばなかった。元の要件のシナリオが分けた要件の振る舞いを確かめる形になり、新しいシナリオが 100 件ほど増える）。

### D4. 保存の確認

分ける前の main spec と分けた後の main spec を比べる確認を、作業用のスクリプトで行う（リポジトリには入れない。この change の後には使わないため）。

- 分ける前の要件の本文の、規範の文（`。` と改行で区切り、MUST / SHALL / SHOULD を含むもの）が、分けた後のどれかの要件の本文に一字一句そのまま現れる
- 分ける前のシナリオ（見出しと中身）が、分けた後のどれかの要件の下にそのまま現れる。中身に行を足したシナリオは一覧にして目で確かめる
- 分ける前の本文の規範ではない文が、分けた後の本文かシナリオに現れる。現れないもの（シナリオへ形を変えて移したもの、D1 で補った句）は一覧にして目で確かめる
- 1.14.1 の `openspec validate --specs --strict` が、分けた後の main specs で通る（PR #56 の worktree の 1.14.1 の実行ファイルで回す）

### D5. 再発を防ぐ

`openspec/config.yaml` の `rules.specs` に「Requirement の本文（見出しから最初の Scenario まで）は 500 文字以内にする。超えるときは振る舞いごとに Requirement を分ける」を足す。1.14.1 になれば validate でも止まるが、`MODIFIED` の本文は change の validate では調べられず、アーカイブの後に初めて見つかるため、書くときに守る。

### D6. 作業の分け方

capability ごとに独立しているので、目標の spec は capability ごとにサブエージェントで作り、D4 の確認はメインエージェントが全 capability にまとめて回す。サブエージェントには D1・D2 の規則と、その capability の対象の要件の一覧を渡す。

この change はコードを変えないので、docs/architecture.md の原則（A1 など）に関わる判断は無い。

## セキュリティ

該当しない。仕様の書き方を変えるだけで、トークン・gh サブプロセス・ネットワーク・URL を開く処理のコードにも振る舞いにも触れない。セキュリティに関わる要件（トークンを漏らさない、オリジンの検査など）も、D1 のとおり規範の文を変えずに分けるので、約束は弱くならない。D4 の確認で、規範の文が 1 つも落ちていないことを確かめる。

## Risks / Trade-offs

- 分けた要件が前提を失って読みにくくなる → D1 で前提を 1 句だけ補うことを許し、補った句は一覧にしてレビューで見る
- 参照（`polling「取得の状態」` など）が、中身の移った要件を指したまま残る → D2 のとおり参照を grep し、移ったものだけ直す。レビューでも見る
- 要件の数が増えて spec が長くなる → 振る舞いごとに見出しが付くので、探しやすさはむしろ上がる。並びは D3 で元の要件の後ろに揃える
- 1.13.2 のままの main ではこの change の `MODIFIED` の長さを調べられない → D4 で 1.14.1 の実行ファイルを使って確かめる
