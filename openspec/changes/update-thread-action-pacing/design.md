# Design

## Context

まとめた操作（リポジトリのグループの既読・Done、アカウントのすべて Done）は、どれも `NotificationStore` から `AccountPoller.perform(_:)` に `ThreadAction` の配列を渡して送る。`perform(_:)` は配列の順に 1 件ずつ、毎回トークンを読み直し、止まっていないかを確かめてから送る。1 件だけの操作（行の既読・Done、通知のクリックでの既読）も、要素が 1 つの配列で同じ `perform(_:)` を通る。

`AccountPoller` は待ちを `sleep: Sleep`（`@Sendable (Duration) async throws -> Void`）のクロージャで注入している。テストではこれに `ManualSleeper` を渡し、取得の間の待ちを `advance()` で 1 つずつ進めて取得の順を制御している。`ManualSleeper.advance()` は最も古い待ちを進めるので、取得の待ちと別の待ちが同じ `ManualSleeper` に並ぶと、どちらが進むかがテストから決められなくなる。

送る間隔の要件は specs/polling/spec.md の「リポジトリのグループの既読化と Done のリクエストの順」にある。

## Goals / Non-Goals

**Goals:**

- `perform(_:)` の中で、2 件目以降の送信の前に 1 秒待つ
- 待ちをテストで差し替え、実時間を待たずに間隔と順を確かめられるようにする。既存のポーリングのテストの待ちの順を変えない

**Non-Goals:**

- 別々の操作（`perform(_:)` の呼び出し）の間の間隔。行の Done を続けて押したとき、それぞれの 1 件目は待たずに送る。1 件ずつの操作はユーザーの手の速さで決まり、1 分に 180 件に届かない
- 2 つのまとめた操作が重なったときの調整（actor の再入で、2 つの `perform(_:)` が交互に送ることがある）。それぞれが 1 秒空けるので、合わせても 1 分に 120 件で、180 件に届かない
- レート制限にかかった後に待って続きを送ること。spec のとおり今の打ち切りのままにする
- 待っている間の表示。対象のスレッドは押したときに一覧から外しているので、出すものが無い

## Decisions

### D1. 間隔の待ちは、取得の待ちと別のクロージャで注入する（A5）

`AccountPoller.init` に `actionSpacing: Sleep`（既定は `{ try await Task.sleep(for: $0) }`）を足し、`perform(_:)` の 2 件目以降の前にこれで待つ。間隔の値（1 秒）は `AccountPoller` の `static let` に置く（`unconditionalFetchInterval` と同じく、ポーラーの振る舞いの定数として）。

- 採らなかった案: 既存の `sleep` を使い回す。取得の待ちと同じ `ManualSleeper` に並び、既存のテストの `advance()` がどちらの待ちを進めるかが変わる。グループの操作のテストが、間隔の待ちで止まる
- 採らなかった案: 前の送信の時刻をポーラーに持ち、`now` で残りを計算して待つ（`RefreshWaiters.remainingWait(now:)` と同じ形）。`perform(_:)` の呼び出しをまたいでアカウント単位で間隔を守れるが、それは Non-Goals で外した範囲で、actor に持つ状態が 1 つ増える。呼び出しの中で毎回 1 秒待つ形なら、状態を持たずに済む

テストの `PollerFixture` は、間隔の待ちに既定ですぐ返して長さを記録するだけのクロージャを渡す（既存のグループの操作のテストが、間隔のために止まらない）。待っている間に止める場合のテストだけ、別の `ManualSleeper` を渡して待ちの途中で止める。

### D2. 待ちの後に、今と同じ確かめ直しを通す（A6）

1 件ごとの「トークンを読み直し、止まっていないか・トークンを捨てていないかを確かめる」処理は、待ちの後に置く。待っている間に無効化・削除・終了でトークンを捨てても、捨てる前に読んだトークンで送らない。待ちが投げた場合（キャンセル）も送らずに打ち切る。`perform(_:)` を呼ぶ `Task` は今もキャンセルしないので、実際に投げるのはテストの `ManualSleeper` だけになる。

送らずに打ち切ったスレッドも、今と同じく `HiddenThreads.endRequest` と `unconditionalRequested = true` を 1 件ごとに通す（次の取得で一覧に戻すため）。

- 採らなかった案: `stop()` で待ちをキャンセルしてすぐ抜ける。待ちの後の確かめ直しで送らないことは同じで、待ちを持ち回る状態（`sleepTask` のような）を増やすだけになる

### D3. 待ちは前の結果にかかわらず入れる

`500` などで続けるときも 1 秒空ける。二次レート制限の点数は結果にかかわらず数えられるため。認証エラー・レート制限・トークン無しで残りを送らないときは、送らないスレッドの前では待たない（送らないので空ける意味が無い）。

### アクターの境界

`perform(_:)` は `AccountPoller`（actor）の上で動く。`actionSpacing` は nonisolated の async クロージャで、`SWIFT_APPROACHABLE_CONCURRENCY` によりポーラーの actor の上で呼ばれ、`Task.sleep` で中断する。中断している間は actor が空くので、取得のループ・再読み込み・別の操作は待たずに進む（A2）。テストの偽物は同期的に待たず、continuation で中断する（A12）。

### docs/architecture.md

変えない。間隔は振る舞いの約束で、spec に書く。コードの構造の原則は増えない。消す・改名する名前も無い。

## セキュリティ

- トークンの流れ: 今と同じ。`TokenProviding` から 1 件ごとに `currentToken(for:)` で読み、そのリクエストにだけ付けて `GitHubAPIClient` に渡す。待っている間はトークンを手元の変数に持たない（待ちの後に読む）。永続化しない。アカウントの削除・無効化・終了で捨てたトークンは、待ちの後の確かめ直しで使わない
- 送る先: 変えない。既存の `markThreadRead` / `markThreadDone` を通るので、オリジン検査・リダイレクトの拒否・キャッシュなしはそのまま掛かる
- gh サブプロセス・URL を開く処理・ログ: 触れない。ログに足すものは無い
- security.md のほかの項目（伏せ字、環境変数の除去、ホスト名の検証、ATS、entitlement、依存、CI）: この変更は送る時刻だけを変えるので、該当しない

## Risks / Trade-offs

- [500 件をすべて Done にすると、送り終えるまで約 8 分かかる] → スレッドは押したときに一覧から外し、条件なしの取得でも隠したままにする（`HiddenThreads` の今の扱い）。その間にアプリを終了すると、残りは送られず、次の起動で一覧に戻る。押し直せば続きから送れる
- [GitHub が点数や上限を変える] → 1 秒はドキュメントのベストプラクティスに合わせた値で、上限の 3 分の 1。それでもレート制限にかかったときは、今の打ち切りと知らせがそのまま効く
- [送り終える前にもう一度すべて Done を押す] → 2 回目の対象は、押したときに一覧に出ているスレッドだけ。送っている途中のスレッドは一覧から外れているので、重ねて送らない
