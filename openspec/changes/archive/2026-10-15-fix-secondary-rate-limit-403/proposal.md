# Proposal

## Why

GitHub は二次レート制限を `403`（または `429`）で返し、待ち時間のヘッダー（`Retry-After`、`X-RateLimit-Remaining: 0`）を付けないことがある。そのときの見分け方は、本文の `message` が二次レート制限（`secondary rate limit`）を示すことだけになる。Mewbell は今、この見分けをスレッドの状態とイベントの取得でしかしていない。

- 通知の一覧の取得（`GET /notifications`）では、待ち時間のヘッダーの無い二次レート制限の `403` が「拒否」として扱われる。拒否の待ち方（60 秒から倍々）には乗るが、レート制限の待ちではないので、ユーザーが再読み込みを押すと 10 秒で取り直してしまう。二次レート制限の間に要求を続けると、GitHub は制限を延ばしたり、締め出したりすることがある。Diagnostics の最後の失敗も `HTTP 403` になり、取得の状態にもレート制限と出ない。
- 既読化・Done・すべて既読では、同じ `403` が状態コードの失敗になり、操作の失敗の知らせに理由（レート制限）が出ない。書き込みの要求は二次レート制限の点数が重いので、操作を続けたときに一番起こりやすいのはこちらになる。

fix-api-client-send-privacy の code-review で、見分け方が経路によって違うことが指摘された。

## What Changes

- 本文で二次レート制限を見分ける判定を、通知の一覧の取得、操作、スレッドの状態とイベントの取得で同じにする。
- 通知の一覧の取得: 待ち時間のヘッダーが無く、本文が二次レート制限を示す `403` を、拒否ではなくレート制限として扱う。待ち時間のヘッダーの無い `429` も同じに扱う。待ち時間が分からないレート制限は、GitHub の推奨（1 分以上待ち、続けば待ちを延ばしていく）に合わせ、拒否と同じく 60 秒から失敗が続くたびに倍にし、15 分を上限とする。レート制限なので、再読み込みや「参加しているスレッドだけにする」の切り替えなどで早めない。
- 既読化・Done・すべて既読: 待ち時間のヘッダーが無く、本文が二次レート制限を示す `403` を、状態コードの失敗ではなくレート制限として扱う。既読化の `429` もレート制限として扱う（今のコードと同じ。spec に書かれていなかった）。
- スレッドの状態とイベントの取得の扱い（待ち時間が分からなければ 60 秒止める）は変えない。

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `github-api`: 「ステータスコードの扱い」「スレッドの既読化のリクエスト」「スレッドを Done にするリクエスト」「すべて既読のリクエスト」の `403` と `429` の扱いを変える。
- `polling`: 「失敗したときの待ち方」に、待ち時間が分からないレート制限の待ち方を足す。

## Impact

- マイルストーン: M4（設定と操作）以降の保守の change。M2 の取得と M3・M4 の操作のエラー処理を揃える。
- 変更するもの: `Mewbell/GitHubAPI/GitHubAPIClient.swift`（一覧と操作の分類、二次レート制限の判定の共有）、`Mewbell/Polling/AccountPoller.swift`（待ち時間が分からないレート制限の待ち）、関連する Polling の型と、そのテスト。UI の文言（`ActionFailureMessage`、取得の状態の表示）は、すでにレート制限を出し分けているので変えない。
- トークン・gh サブプロセス・ネットワーク・URL を開く処理: ネットワークの応答の分類に触れる。送り先、ヘッダー、リダイレクト、キャッシュは変えない。レスポンスの本文は、見分けるために `message` だけを読み、保持・表示・ログ出力はしない（今のスレッドの状態とイベントの取得と同じ）。トークンは今までどおりメモリにだけ持ち、永続化しない。
