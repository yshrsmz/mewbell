# Proposal

## Why

すべて Done（`update-account-heading-actions`）とリポジトリのグループの既読・Done は、スレッドごとのリクエストを 1 件ずつ順に送るが、送る間隔は空けていない。GitHub の REST API の二次レート制限は 1 分あたり 900 点までで、書き込み（`PATCH`・`DELETE`）は 1 件 5 点なので、1 分に送れるのは 180 件までになる。1 件の往復が数百ミリ秒なら、一覧（最大 500 件）のスレッドをおよそ 180 件より多くまとめて Done にすると、途中で二次レート制限にかかる見込みが高い。今は spec のとおりそこで打ち切り、残りは次の取得で一覧に戻り、知らせが 1 つ出る。ユーザーはしばらく待ってからもう一度押すしかない。

GitHub のドキュメント（[Best practices for using the REST API](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)）は、書き込みを多く送るときは並行させずに順に送り、各リクエストの間を少なくとも 1 秒空けることを勧めている。これに合わせて送る間隔を空け、まとめた操作が途中で止まらないようにする。

マイルストーン: M4「設定と操作」の追補。`add-repository-group-actions` と `update-account-heading-actions` で入れたまとめた操作の送り方を改める。

## What Changes

- まとめた操作（リポジトリのグループの既読・Done、アカウントのすべて Done）で、2 件目以降のリクエストは、前のリクエストの結果が出てから 1 秒待って送る。1 秒は 1 分に 60 件までになり、二次レート制限の 180 件を大きく下回る
- 1 件だけの操作（スレッドの行の既読・Done、通知のクリックでの既読）は待たない。1 件目のリクエストも待たずに送る
- 待っている間にアカウントが止まった、ポーリングを止めた、トークンを捨てたときは、今と同じく残りを送らない（待ちの後に確かめ直す）
- 前のリクエストの結果にかかわらず（`500` などで続けるときも）同じ間隔を空ける。認証エラーとレート制限で残りを送らない扱いは変えない
- 対象のスレッドはこれまでどおり押したときに一覧から外すので、待ち時間は一覧には出ない。500 件をすべて Done にすると、送り終えるまで約 8 分かかる

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `polling`: 「リポジトリのグループの既読化と Done のリクエストの順」に、2 件目以降のリクエストの前に 1 秒待つことと、待っている間に止まったときの扱いを足す。「アカウントのすべて Done のスレッドごとの扱い」はこの要件に従うので、すべて Done にもそのまま効く

`github-api` は変えない（送るリクエストとレスポンスの扱いは同じ）。`ui` も変えない（押したときの一覧の動きと確認の表示は同じ）。

## Impact

- コード: `Mewbell/Polling/AccountPoller+ThreadActions.swift`（`perform(_:)` の送る間隔）、`Mewbell/Polling/AccountPoller.swift`（間隔の待ちを差し替えられるようにする）、テスト
- トークン: 触れる。1 回の操作で送るリクエストの数と送り先は変えず、間隔を空けるだけ。待っている間もトークンを手元に持ち続けず、1 件ごとに読み直す今の形を保つ。トークンはこれまでどおりメモリ上の actor にだけ持ち、永続化しない
- ネットワーク: 触れる。新しい経路は作らず、既存の `GitHubAPIClient` の既読・Done のメソッドを通す（オリジン検査・リダイレクトの拒否・キャッシュなしはそのまま掛かる）
- URL を開く処理: 触れない
- gh サブプロセス: 触れない
- 永続化: しない
