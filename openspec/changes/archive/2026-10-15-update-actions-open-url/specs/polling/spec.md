## MODIFIED Requirements

### Requirement: スレッドのイベントの取得

Mewbell はアカウントごとに、一覧のスレッドのイベント（github-api「スレッドのイベントの決定」）と件名の状態（github-api「スレッドの状態の決定」）を取得し、スレッドの ID と `updated_at` の組ごとにメモリにだけ覚えなければならない（MUST）。種類が Release でリリースの ID を持つスレッド（`subject.url` が API ベース URL と同じオリジンで、パスが API ベース URL のパスに続く `repos/<owner>/<name>/releases/<1〜20 桁の数字>` で、`<owner>/<name>` がスレッドのリポジトリと一致するもの）については、イベントと状態の代わりにリリースのタグ（github-api「リリースのタグの取得のリクエスト」）を取らなければならない（MUST）。種類が `WorkflowRun` か `CheckSuite` のスレッドについては、イベントと状態の代わりに、そのスレッドのワークフローの実行（run）の ID（github-api「ワークフローの実行の検索のリクエスト」）を取らなければならない（MUST）。以下この要件の「イベント」は、イベントと状態の組と、リリースのタグと、run の ID を指す（イベントが「無い」でも状態は分かることがある）。覚えたイベントは、アプリの終了で捨て、ディスクや設定に書いてはならない（MUST NOT）。一覧のスレッドには、ID と `updated_at` がどちらも一致する覚えたイベントだけを付けなければならない（MUST）。`updated_at` が変わったスレッドのイベントは取り直さなければならない（MUST）。一覧から消えたスレッドの分は捨てなければならない（MUST）。アカウントが止まった（スコープ不足・認証エラー）ときは、すべて捨てなければならない（MUST）。

取得は、イベントの取得を待っている（取得したことが無いか、前回が一時的な失敗だった）番号を持つスレッド、リリースの ID を持つ Release のスレッド、種類が `WorkflowRun` か `CheckSuite` のスレッドのうち、既読・Done・すべて既読で一覧から隠しているもの以外だけを対象にし、次の順に行わなければならない（MUST）。

1. 通知の取得が `200` で終わり、その前にもこのポーリングで一覧を取得できていたとき: 前の一覧に無かったスレッドと、前の一覧より `updated_at` が新しくなったスレッド（新着）のうち、更新日時が新しい順に最大 10 件のイベントを取ってから、その一覧を取得の状態として知らせる。この取得に 20 秒より長くかけてはならず（MUST NOT）、終わらなかったスレッドは一時的な失敗として扱う
2. 取得の状態を知らせた後（`200` でも `304` でも）、次の取得を待ち始める前に: まだ待っているスレッドのうち、更新日時が新しい順に最大 30 件のイベントを取り、取れたものを付けた一覧を知らせ直す。この取得にも 20 秒より長くかけてはならず（MUST NOT）、終わらなかったスレッドは一時的な失敗として扱う。同じ回の 1. で取ったスレッドは、失敗していても取り直してはならない（MUST NOT）

新着の判定に使う「前の一覧」と、捨てずに残す記録は、既読・Done・すべて既読で隠したスレッドを含む、API が返した一覧にしなければならない（MUST）（既読にできずに一覧に戻ったスレッドを、新着として取り直さないため）。1. と 2. の取得の最中にユーザーが再読み込みを押したら、その取得をやめて（取り終えた分は記録し、取れていない分は失敗として数えない）、再読み込みの取得を待たせてはならない（MUST NOT）。今の通知の取得の後にもう 1 回取得する再読み込みを待っている間（通知の取得の最中に押されたとき）は、1. と 2. の取得を始めてはならない（MUST NOT）。再読み込みで始めた取得そのものの 1. は、ほかの取得と同じく行わなければならない（MUST）。1 つのアカウントで同時に取るスレッドは 4 件までにしなければならない（MUST）。イベントが「無い」だったスレッドは、その `updated_at` の間は取り直してはならない（MUST NOT）。一時的な失敗と認証の失敗のスレッドは、次の機会に取り直さなければならない（MUST）。ただし、同じ `updated_at` のまま 3 回続けて失敗したスレッドは、その `updated_at` の間は取り直してはならない（MUST NOT）（リポジトリを移した後のリダイレクトのように失敗し続けるスレッドで、レート制限の残りを使い続けないため）。

イベントの取得の結果（失敗とレート制限を含む）で、通知の取得の状態、打ち切り、ポーリングの間隔、連続した失敗の数、最後の取得の失敗（「取得の状態」）を変えてはならない（MUST NOT）。イベントの取得がレート制限になったら、制限が解ける時刻（ヘッダーで分からないか 60 秒より早いときは 60 秒後）まで、そのアカウントのイベントの取得を始めてはならない（MUST NOT）。その間も通知の取得は続けなければならない（MUST）。トークンを持っていないときはイベントを取ってはならない（MUST NOT）。イベントには、そのアカウントのトークンだけを付けなければならない（MUST）。

イベントを取っている間に既読・Done・すべて既読で一覧から外したスレッドを、イベントを付けて知らせ直すときに一覧に戻してはならない（MUST NOT）。ポーリングを止めた後に返ったイベントで、状態を書き換えてはならない（MUST NOT）。

#### Scenario: 新着のイベントを取ってから知らせる

- **GIVEN** `github.com/alice` の前の取得の一覧にスレッド `123` が無かった
- **WHEN** 次の取得で `123` が返り、そのイベントが Commented by `bob` と決まる
- **THEN** `123` を含む一覧は、`123` に Commented by `bob` を付けた状態で初めて知らされる

#### Scenario: 最初の一覧はイベントを待たずに知らせる

- **GIVEN** `github.com/alice` のポーリングを始め、最初の取得で 12 件のスレッドが返る
- **WHEN** Mewbell が取得の状態を知らせる
- **THEN** 一覧はイベントを取る前に知らされ、その後で 12 件のイベントを取って一覧を知らせ直す

#### Scenario: 新着が多い

- **GIVEN** `github.com/alice` の次の取得で新着が 15 件ある
- **WHEN** Mewbell が取得の状態を知らせる
- **THEN** 更新日時が新しい 10 件はイベントを付けて知らされ、残りの 5 件はイベントなしで知らされる
- **AND** 残りの 5 件のイベントは、知らせた後に取って知らせ直す

#### Scenario: 変わっていないスレッドは取り直さない

- **GIVEN** `github.com/alice` のスレッド `123` のイベントを `updated_at` 12:00 で覚えている
- **WHEN** 5 分ごとの条件なしの取得で、`123` が同じ `updated_at` で返る
- **THEN** `123` のイベントのリクエストは送られず、覚えたイベントが付く

#### Scenario: updated_at が進んだら取り直す

- **GIVEN** `github.com/alice` のスレッド `123` のイベント Commented by `bob` を `updated_at` 12:00 で覚えている
- **WHEN** 次の取得で `123` が `updated_at` 12:30 で返る
- **THEN** `123` のイベントを取り直し、Commented by `bob` は付けない

#### Scenario: イベントの取得の失敗は取得の状態を変えない

- **GIVEN** `github.com/alice` の通知の取得が `200` で、イベントの取得が `502` になった
- **WHEN** Mewbell が取得の状態を決める
- **THEN** 状態は「取得できた」で、連続した失敗の数と最後の取得の失敗は変わらない
- **AND** そのスレッドはイベントなしで一覧に出て、次の機会にイベントを取り直す

#### Scenario: 失敗し続けるスレッド

- **GIVEN** `github.com/alice` のスレッド `123` のイベントの取得が、同じ `updated_at` のまま 3 回続けてリダイレクトで失敗した
- **WHEN** 次の取得が成功する
- **THEN** `123` のイベントのリクエストは送られず、`123` はイベントなしで一覧に出る
- **AND** `123` の `updated_at` が進んだら、また取り直す

#### Scenario: イベントの取得のレート制限

- **GIVEN** `github.com/alice` のイベントの取得が、10 分後に解けるレート制限になった
- **WHEN** 1 分後に通知の取得が成功する
- **THEN** 通知の取得の状態は「取得できた」で、10 分後までイベントのリクエストは送られない

#### Scenario: イベントを取っている間に既読にした

- **GIVEN** `github.com/alice` の新着のスレッド `123` のイベントを取っている
- **WHEN** その間にユーザーが `123` を既読にし、その後でイベントが返る
- **THEN** 知らせ直す一覧に `123` は戻らない

#### Scenario: 止まったら捨てる

- **GIVEN** `github.com/alice` のスレッドのイベントを覚えている
- **WHEN** `alice` が「認証エラー」で止まる
- **THEN** 覚えていたイベントはすべて捨てられる

#### Scenario: 新着の Release のタグを取ってから知らせる

- **GIVEN** `github.com/alice` の前の取得の一覧にスレッド `555` が無かった
- **WHEN** 次の取得で、種類が Release で `subject.url` が `https://api.github.com/repos/octo/app/releases/413167889` のスレッド `555` が返る
- **THEN** `GET https://api.github.com/repos/octo/app/releases/413167889` が `alice` のトークンで送られる
- **AND** `555` を含む一覧は、`555` にリリースのタグを付けた状態で初めて知らされる

#### Scenario: リリースの ID を持たない Release

- **GIVEN** `github.com/alice` の種類が Release のスレッドの `subject.url` が無いか、`https://api.github.com/repos/other/repo/releases/1` のようにスレッドのリポジトリと一致しない
- **WHEN** Mewbell がイベントを取るスレッドを選ぶ
- **THEN** そのスレッドにはリクエストを送らない

#### Scenario: 新着の承認リクエストの run を取ってから知らせる

- **GIVEN** `github.com/alice` の前の取得の一覧にスレッド `777` が無かった
- **WHEN** 次の取得で、種類が `WorkflowRun` でリポジトリが `octo/app` のスレッド `777` が返る
- **THEN** `GET https://api.github.com/repos/octo/app/actions/runs?status=waiting&per_page=6` が `alice` のトークンで送られる
- **AND** `777` を含む一覧は、`777` に見つけた run の ID を付けた状態で初めて知らされる

#### Scenario: 種類が CheckSuite のスレッドは subject.url が無くても run を探す

- **GIVEN** `github.com/alice` の種類が `CheckSuite` のスレッドの `subject.url` が無く、件名が `CI workflow run failed for main branch`
- **WHEN** Mewbell がイベントを取るスレッドを選ぶ
- **THEN** そのスレッドは run を探す対象になる
