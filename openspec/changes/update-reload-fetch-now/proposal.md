# Proposal

## Why

再読み込みボタンを押しても、一覧がすぐに変わらない。今は「次の取得を `If-Modified-Since` なしにする」だけで、取得そのものは次の予定の時刻（`X-Poll-Interval` と 60 秒の大きいほう）まで待つ（`fix-stale-notification-list` の D2）。押した後に見た目も変わらないので、ユーザーには壊れているように見えた。

実例: `Fission-AI/OpenSpec#2064`（`reason: subscribed`）が、`updated_at` が `Last-Modified`（その時点の最新の `updated_at`）より古いまま受信箱に入ったため `304` に隠れた。Gitify には出ているのに Mewbell には出ず、再読み込みを押してもすぐには出なかった。ログでは、押してから次の条件なしの取得まで 1 分近くかかっていた。

マイルストーン: M4 の途中に入れる改善（`add-thread-actions` の後、`add-settings` の前）。

## What Changes

- 再読み込みボタンを押したら、取得を続けているアカウントは次の予定を待たずに、すぐ `If-Modified-Since` なしで取得する。**BREAKING**（spec 上）: 「ユーザーの操作で間隔より早く取得しない」の例外になる
- 連打で API を叩きすぎないよう、押したことによる取得は、そのアカウントの前の取得を始めてから 10 秒より早くはしない。レート制限で待っているアカウントは、押しても早めない
- ボタンは押したときに押した反応を見せ、押してから「アカウントの読み直し」と「押したことによる各アカウントの取得」が終わるまで、読み込み中の表示（進捗のインジケーター）に替えて押せなくする
- ポップオーバーを開いただけでは今までどおり取得を早めない
- CLAUDE.md の「ポーリングは API の指示に従う」に、再読み込みの例外を書き足す

## Capabilities

### New Capabilities

なし

### Modified Capabilities

- `polling`: 「条件付きリクエスト」の再読み込みの Scenario と、「ポーリングの間隔」の「ユーザーの操作で早めない」を、再読み込みだけの例外（10 秒の下限、レート制限中は早めない）に変える
- `ui`: 「再読み込みボタン」で、すぐ取得すること、押した反応、読み込み中の表示を足す

## Impact

- コード: `Mewbell/Polling/AccountPoller.swift`（待ちを途中で起こす、取得の完了を待てるようにする）、`Mewbell/Polling/NotificationStore.swift`（再読み込みの開始と読み込み中の状態）、`Mewbell/App/MenuBarContentView.swift`（ボタンの表示）、テスト、CLAUDE.md、README
- ネットワーク: 触れる。送るリクエストは今までどおりの `GET /notifications` で、送る時刻が早まるだけ。送り先・トークンの付け方・オリジン検査・リダイレクトの拒否は変えない（security.md の「ネットワーク」の約束はそのまま）
- トークン・gh サブプロセス・URL を開く処理: 触れない。トークンは今までどおりメモリにだけ持ち、永続化しない。止まっているアカウントの再開でトークンを取り直すのは今までどおり
- API の利用量: ユーザーが押した回数だけ増える。1 アカウントあたり 10 秒に 1 回が上限で、条件なしの取得は 1 回につき 1〜数リクエスト。上限の 5,000 回/時に比べて小さい
