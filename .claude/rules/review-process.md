# 実装完了後のレビュー

実装（`/opsx:apply` の tasks）が終わったら、archive や PR の ready 化の前に、メインエージェントとは別のコンテキストでレビューする。メインエージェントの考えや経緯が混ざるとセルフレビューになるため、コンテキストを必ず分ける。

## 手順

1. **simplify**: Agent ツールで新しいサブエージェントを起動する（`subagent_type: "general-purpose"`、`model: "opus"`。fork は会話を引き継ぐので使わない）。サブエージェントには `simplify` スキルを実行させる
2. **code-review**: simplify の変更が入った後に、もう 1 つ新しいサブエージェントを同じ設定で起動し、`code-review` スキルを effort `medium` で実行させる（Skill の args に `medium` を渡す）
3. メインエージェントは、サブエージェントが報告した指摘を受け取って対応する。指摘ごとに「直した / 直さない（理由）」を決め、直さないものは理由を PR 本文に書く
4. 直した量が多いとき（ロジックの変更を含むとき）は、手順 2 をまた新しいサブエージェントで実行する

## サブエージェントへの渡し方

- 渡すのはレビューの対象だけにする: ブランチ名、比較の起点（`main`）、対応する `openspec/changes/<change>/` のパス、リポジトリのルール（CLAUDE.md と `.claude/rules/`）と設計方針（`docs/architecture.md`）を読むこと。設計方針は経緯ではなく今の方針なので、渡してよい。指摘が原則に関わるときは原則の ID を添え、原則そのものへの異議は異議として分けて報告させる
- メインエージェントの設計判断の理由、迷った点、「ここは問題ない」といった評価は渡さない
- simplify は変更をそのまま作業ツリーに入れる。code-review は指摘を報告させるだけで、修正はさせない（`--fix` を付けない）
- サブエージェントの作業はコミットさせない。コミットはメインエージェントが内容を確かめてから行う

## 指摘の直し方

- 指摘を直すか直さないかは、`docs/architecture.md` の「指摘の仕分けとの関係」に照らして決める。原則が退けた案を求める指摘は、原則の ID を理由に直さない。方針が決めていない論点を決めたら、change をまたいで効くものは同じ change で `docs/architecture.md` に足す
- 指摘はその箇所だけを繕って直さない。同じ部品に指摘が集まったら、その部品の目標の形（型・置き場所・責務・兄弟の箇所との関係）を先に決め、直し方はその形に合うかで決める。繕った形は次のレビューで新しい指摘を生む
- 目標の形はメインエージェントひとりで決めない。経緯を渡さない新しいサブエージェントに、`openspec/specs/` と change の delta spec（要件）、`docs/architecture.md` の原則、Apple のプラットフォームの慣用、最小であること（それぞれの型や抽象がどの要件・どのテストのためにあるか）で評価させ、要件から考えた最小の案と比べさせる。結果を AskUserQuestion でユーザーに示し、決まってから実装する。決めた形は change の design.md に「今の形」として書く
- change の範囲を超えて新しい型・抽象・ファイルを足す直し方は、指摘を満たすためだけに足していないかを確かめ、AskUserQuestion で確かめてから行う
- 修正をサブエージェントに任せるときは、提出の前に、自分の差分をレビューと同じ観点（使われないもの、重複、置き場所、API の形、兄弟の箇所との対称性、慣用）で見直させる

## 記録

- tasks.md の最後のタスクグループに、simplify と code-review のタスクを入れる
- PR 本文の Test plan に、simplify と code-review をサブエージェントで実行したこと、指摘の件数と対応結果を書く
